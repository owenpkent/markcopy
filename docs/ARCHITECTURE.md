# Architecture

MarkCopy is a custom-webview VS Code extension that previews nine kinds of document through four webviews. Markdown, CSV/TSV, spreadsheets, Word documents, and presentations share one: the Node extension host renders each to HTML (`markdown-it`, `src/csv.ts`, `src/xlsx/`, `src/docx/read/`, and `src/pptx/read/` respectively) and the webview displays it. PDF and STL each have their own, where the host only supplies bytes and the rendering happens in the webview (pdf.js, and Three.js). LaTeX reuses the PDF webview outright rather than adding a fifth: the host compiles the document to a PDF first, then hands over the same bytes the PDF preview would (see [LaTeX preview](#latex-preview)). Video has its own as well, and is the one case where the host supplies neither HTML nor bytes: it hands the webview a resource URI and the `<video>` element streams the file itself. In all of them, interaction (context menu, clipboard, Mermaid, PNG capture, CSV cell editing) happens in the webview. This split is deliberate: the webview is a browser context, and the clipboard operations we need (writing `text/html`, capturing PNGs) only exist there.

## Big picture

```
 ┌──────────────────────────┐        postMessage        ┌───────────────────────────┐
 │  Extension host (Node)    │  ───────────────────────► │  Webview (browser/iframe) │
 │  src/extension.ts         │   render / scrollToLine / │  src/webview/main.ts      │
 │  src/render.ts (markdown) │   copyAll                 │  media/preview.css        │
 │  src/csv.ts    (csv/tsv)  │  ◄─────────────────────── │                           │
 │  markdown-it, highlight.js│   revealLine / toast /    │  Mermaid, html-to-image,  │
 │  source-line mapping      │   ready                   │  context menu, clipboard  │
 └──────────────────────────┘                           └───────────────────────────┘
        dist/extension.js                                        media/webview.js
        (esbuild.js, node)                                   (esbuild.web.js, browser)
```

All four take the same path. The host decides how to turn the open document into
HTML (`markdown-it` for Markdown, `src/csv.ts` for CSV/TSV, `src/xlsx/` for a
workbook, `src/pptx/read/` for a deck) and sends it in the same `render` message with a `kind` field; the
webview sanitizes the HTML, picks its layout from `kind`, and otherwise treats
them identically. That is why the context menu, the clipboard actions, the themes,
the PDF export, and scroll sync all work on a CSV grid or a spreadsheet sheet
without knowing what it is. A workbook or a deck reaches that same webview from a
custom editor rather than from `update()`, because it is binary and never becomes a
TextDocument (see [Spreadsheet preview](#spreadsheet-preview)).

The PDF preview uses the same host/webview split with its own custom editor and bundle:

```
 ┌──────────────────────────┐        load (bytes,        ┌───────────────────────────┐
 │  Extension host (Node)    │        workerSrc)          │  PDF webview (browser)    │
 │  src/pdfEditor.ts         │  ───────────────────────► │  src/webview/pdf.ts       │
 │  workspace.fs.readFile    │  ◄─────────────────────── │  pdf.js + module worker   │
 │  (CustomReadonlyEditor)   │        ready / toast       │  canvas render, copy      │
 └──────────────────────────┘                           └───────────────────────────┘
        dist/extension.js                          media/pdf.js + media/pdf.worker.js
```

Five entry bundles (plus the Markdown webview's lazily-loaded `media/chunk-*.js` files) are produced from one TypeScript source tree by two esbuild scripts:

- `esbuild.js` bundles `src/extension.ts` to `dist/extension.js` for Node (`vscode` left external).
- `esbuild.web.js` bundles the browser code: `src/webview/main.ts` to `media/webview.js` as an ES-module, code-split build (Mermaid, KaTeX, html-to-image, and Turndown load lazily via dynamic `import()` as separate `media/chunk-*.js` files, only when first needed; DOMPurify stays eager), `src/webview/pdf.ts` plus the pdf.js worker to `media/pdf.js` and `media/pdf.worker.js` (esm), `src/webview/stl.ts` to `media/stl.js` (esm, Three.js bundled in), and `src/webview/video.ts` to `media/video.js` (esm, no library at all). Code-splitting drops the initial `media/webview.js` from roughly 8.5MB to about 19KB, since the heavy libraries are only fetched on demand (a diagram or equation present, Copy as PNG, Copy as Markdown).

See [PDF preview](#pdf-preview) below for the PDF data flow in detail.

`tsc --noEmit` type-checks the whole tree; esbuild does the actual transpiling and bundling. `tsconfig.json` uses `module: ESNext` and `moduleResolution: Bundler` so the ESM-only dependencies (Mermaid, markdown-it-anchor) type-check cleanly.

## Rendering pipeline

1. The user opens the preview. `openPreview` creates a `WebviewPanel` (beside the editor, `retainContextWhenHidden: true`), or `PreviewEditorProvider` is handed one for a document opened as a MarkCopy tab; either way `registerPreview` sets the HTML shell and wires the messages (see [The two preview surfaces](#the-two-preview-surfaces)).
2. `update()` reads the document text, calls `md.render(source, { resolveImage })` (see [Local images](#local-images) below), and posts a `render` message carrying the HTML, the raw source, the active style profile, the theme (`markcopy.theme`), any `markcopy.mermaid` config, and the current `syncScroll` / `autoPreview` settings.
3. In the webview, `render()` sets `#content.innerHTML`, applies the style profile and theme to `body` (`dataset.style`, `dataset.mcTheme`), splits the source into `sourceLines` (used later for block "copy as Markdown"), (re)initializes Mermaid with the theme and any `markcopy.mermaid` config, then upgrades every Mermaid placeholder into an SVG and every math placeholder into a KaTeX render (see [Math (KaTeX)](#math-katex) below).
4. On each edit, `onDidChangeTextDocument` re-runs `update()`, so the preview is live. Those runs are coalesced over an 80ms window: a Markdown document is cheap to re-render per keystroke, but a CSV costs a delimiter sniff, a full parse, and a string-built grid of up to `markcopy.csv.maxRows` rows. A cell edit's own writeback calls `update()` directly instead, cancelling anything pending, so the grid learns the new document version without waiting out the debounce (see [CSV editing](#csv-editing)).

### The two preview surfaces

The same preview reaches the reader two ways. `openPreview` builds the "to the side" panel, at most one at a time, retargeted as focus moves between documents. `PreviewEditorProvider` is a `CustomTextEditorProvider` registered for the `markcopy.markdownPreview` and `markcopy.csvPreview` viewTypes, both contributed at `"priority": "option"`: they appear in **Reopen Editor With...** and can be made the default for a glob, but they never claim a file on their own, so the text editor stays what opens a `.md` out of the box. (The viewTypes for PDF, workbooks, decks, STL, and video are `"default"` instead: those files have no useful text form to open into. LaTeX is `"option"` like these two, for the opposite reason; see [LaTeX preview](#latex-preview).) Markdown was briefly moved to `"default"` and moved back, and the reasoning is worth keeping: a `.md` is not a `.pdf`, it is a file people edit all day, and an extension installed for its copy menu taking over every Markdown file on an update is a bigger thing to do than the one click it saves is worth. `markcopy.openRendered` below buys the same result without the ambush.

That pair of `editor/title` buttons is how a reader gets between the two views, and each swaps the tab in place. `markcopy.openSource` (**Show Source**, `$(go-to-file)`) is contributed on `activeCustomEditorId` and calls `showTextDocument` at `ViewColumn.Active`; `markcopy.openRendered` (**Show Preview**, `$(open-preview)`) is contributed on `editorLangId` or a matching `resourceExtname` and calls `vscode.openWith` at the same column, picking the viewType from `previewKind`. The extension half of that `when` clause exists for the same reason `previewKind`'s extension fallback does: another extension or a `files.associations` entry can map a `.csv` to some other language, and gating the button on the language id alone left it hidden on exactly the files the fallback was written for. Both sit at `navigation@0`, and their `when` clauses are mutually exclusive, so the leftmost button is whichever direction the reader can currently go and the pair reads as one control rather than two icons.

`ViewColumn.Active` keeps either direction from splitting the editor, but it is not enough on its own to keep the group down to one editor on the file, and what decides that turns out to be VS Code's _preview mode_, the italic tab a single click opens. A preview-mode tab is replaced by the next thing opened on it; a tab from `vscode.openWith`, or one the reader pinned, is not, and gets opened alongside instead. Neither button can know which it is looking at, so both call `closeStaleEditor`, which closes the leftover editor on that URI in `activeTabGroup` through `window.tabGroups.close`. It skips a pinned tab, since pinning is the reader saying "keep this one", and a dirty _text_ editor, whose unsaved changes are not a layout button's to discard; a preview tab needs no such guard, because the document behind it stays open as the text editor the call just opened. The cost is that the toggle leaves two tabs in those cases, which is the right way round.

`openSource` also adds the document to `dismissedPreviews`, because asking for the source is a request to read the text, and auto-preview answering that click by opening the side panel would hand back the very layout the reader just left (see [Auto-open preview](#auto-open-preview)). `openRendered` deletes it again, on the same footing as an explicit `markcopy.openPreview`.

Both live in one `previews` set, and `side` points at whichever member is the panel. Document changes, setting changes, theme changes, and editor-to-preview scroll sync fan out over the set; the commands act on `activePreview()`, the focused tab or else the panel. The debounce timer is per preview, since one shared timer would let typing in one document cancel another's pending render. Only two things are surface-specific: an editor tab's title belongs to VS Code (so `update()` leaves it alone), and a tab never retargets, because a custom text editor is bound to its document for life. That second point is why following a Markdown link from a tab opens the target as another tab (`vscode.openWith`), handing the new preview the `#fragment` to reveal once it has registered.

Because the document behind a tab is an ordinary `TextDocument`, nothing else has to change: live re-render, source-line mapping, scroll sync into any text editor open on the same file, and CSV writeback through `WorkspaceEdit` (undo included) all work exactly as they do for the panel. This is the difference from the workbook, deck, PDF, STL, and video editors, which are `CustomReadonlyEditorProvider`s over bytes that never become a `TextDocument`.

### Source-line mapping

`render.ts` tags top-level block tokens with `data-source-line` (the token's starting line). This attribute powers two features:

- **Scroll sync:** see [Scroll sync](#scroll-sync) below.
- **Block Markdown (the "Markdown" row under Copy as for a block):** for a clicked block, the webview finds its `data-source-line`, finds the next block's line, and slices `sourceLines` between them (verbatim source). The "Markdown" row under Copy as for a selection is different: it converts just the selected HTML to Markdown with Turndown (`turndown` + `turndown-plugin-gfm`), so partial and multi-block selections come through exactly.

`render.ts` also emits `data-source-end` (the token's exclusive end line) beside `data-source-line` on the same level-0 blocks and on block math. Footnote items carry no range, because the footnote plugin does not give their tokens a map. The pair is what edit mode uses to know which lines of `source` a block covers. Fenced code that goes through highlight.js is returned by markdown-it as finished markup that drops token attributes, so it carries neither attribute and is not editable.

### Markdown edit mode

`src/webview/editMode.ts` draws the lock/pencil pill (Markdown kind only; the mode is kept in `vscode.getState`) and the block editor. In edit mode a click on a top-level block that has both attributes swaps it for a box holding a transparent `<textarea>` over a backdrop `<div>` painted by `src/webview/mdHighlight.ts`. The two layers share every text metric, so native undo, selection, and IME keep working, and the backdrop is built only from HTML-escaped pieces. The lines `[start, end)` come from the `source` of the render on screen, minus trailing blank lines, which are re-appended on commit.

Every commit carries an incrementing `editId` and the `docKey` (the document URI string) of the render it was made from. The host refuses the edit unless `docKey` equals the URI the preview now shows, because a side preview can be retargeted while a commit is in flight and an edit must never land in another file that happens to hold the same text. Whatever the outcome (applied, stale, unchanged, wrong document, apply failure), the host answers with a `render` that carries `ackEdit: editId`. Until that render arrives the line numbers on screen predate the edit, so no editor opens while a commit is unanswered: a block clicked meanwhile is queued by the line it will start on after the edit (`line >= endLine ? line + delta : line`) and opened when the render with `ackEdit >= editId` arrives. If no answer comes within 3 seconds the pending state is dropped. In edit mode the editable top-level blocks are tab stops (`tabindex=0`, tracked with `data-mc-edit-tab` so a tabindex the block already had is left alone); Enter or F2 opens the focused block, Escape cancels and refocuses it, and Ctrl/Cmd+Enter commits and refocuses the block at the same start line once the answering render arrives.

While an editor is open, `main.ts` holds back incoming `render` messages (only the latest is kept) and applies it when the editor closes. A render for a different document closes the editor without committing.

Commit posts `editBlock` (see below). The host never trusts the lines blindly: `planBlockEdit` in `src/blockEdit.ts` requires integer lines with `0 <= startLine < endLine <= lineCount`, string `original` and `text` no longer than 1,000,000 characters, and that the document's text for those lines still equals `original` (compared with line endings normalized). The replaced span ends before the last line's terminator, so a final line without a newline and CRLF documents need no special case; the replacement is written with the document's own EOL. On a mismatch nothing is applied and the webview shows "The document changed; edit not applied." The edit is a `WorkspaceEdit` and the document is not saved.

### Scroll sync

Both directions map through the same structure: a list of `Anchor`s (`{ line, offset }`) pairing each `data-source-line` block with its offset in the scroll container. `src/webview/scrollSync.ts` holds the arithmetic, free of the DOM and unit-tested: `offsetForLine` and `lineForOffset` interpolate linearly between the two anchors bracketing their argument, so the sync tracks a drag continuously instead of snapping from one block to the next, and round-trips a position back to itself rather than drifting as the two surfaces bounce off each other. A synthetic final anchor pairs the end of the document with the container's maximum scroll, so the last screenful maps proportionally too. Measured anchors at or past that maximum are dropped first, since the preview keeps 120px of room to scroll past the end and a closing block sitting in it would otherwise leave the synthetic anchor unable to extend the list. For a grid truncated by `markcopy.csv.maxRows` the end is the last rendered row, not the file's last line, which would otherwise interpolate the final pixels across every unrendered row.

Anchors are measured once and cached, because a long document has hundreds of them and re-measuring every scroll frame costs a forced layout each time. The cache is dropped on render, on resize, and whenever the content's height changes underneath it (a late image, font, or diagram settling). Candidates over `MAX_ANCHORS` (600) are thinned by `sample()`: a 5000-row CSV grid contributes one candidate per row, and interpolating across a sampled subset is visually identical. A candidate is anything carrying `data-source-line`, which covers both layouts: `src/render.ts` puts one on each Markdown block, and `src/csv.ts` puts one on every grid body row. The grid's header row is excluded deliberately, since it is sticky and its position tracks the scroll rather than the content, so `csv.ts` omits the attribute there. An empty attribute value is skipped rather than read as line 0. The CSV layout also scrolls its own `.mc-csv-wrap` rather than the page, which `scroller()` accounts for.

The two surfaces drive each other, so every move one makes returns as a request to move the other. Two symmetric rules break the loop instead of letting them fight:

- The webview does not report a scroll it performed itself (`suppressSync` / `syncSuppressedUntil`), and drops an incoming `scrollToLine` that arrives within `SYNC_ECHO_MS` (250ms) of the reader's own scrolling, since it can only be the echo of what they are already doing.
- The host does not echo a visible-range change caused by its own `revealRange` (`revealEcho` / `revealedAt` in `extension.ts`).

`markcopy.syncScroll` gates both directions: `syncScrollEnabled()` is checked in the host's visible-ranges listener and again in `revealEditorLine`, so with the setting off neither surface follows the other.

### Local images

`render.ts`'s `rewriteImageSrc` routes every rendered `<img>` through an optional `env.resolveImage(src)` hook; when no hook is supplied (plain unit tests, for instance) the `src` passes through unchanged. In the running extension, `extension.ts` supplies that hook: `preview-utils.ts`'s `localImageRef` classifies the `src` first, so remote (`http(s):`), `data:`, `blob:`, and already-resolved URIs are left alone while relative and absolute paths are flagged for resolution. `resolveImageSrc` then resolves a flagged path against the document's URI and turns it into a webview-safe URI with `webview.asWebviewUri`. For that URI to actually load, the webview's `localResourceRoots` must cover the target folder, so `resourceRoots()` widens it to the document's workspace folder (or its own directory, if it isn't inside a workspace), and `openPreview` re-applies `panel.webview.options` whenever the previewed document changes.

### Footnotes

`render.ts`'s `addFootnotes` wires in `markdown-it-footnote` (gated on `markcopy.footnotes`), then patches around three of its rough edges. The plugin's own `footnote_tail` core rule silently drops a `[^label]: text` definition whose label is never referenced anywhere in the document -- there is no `env.footnotes.list` entry to re-emit it under -- which in a live preview reads as the author's own text vanishing as they type. `footnoteFixups`, a core rule that runs immediately before `footnote_tail`, re-parses each unreferenced definition's original source lines as ordinary Markdown (with the `footnote_def` block rule turned off for that one nested parse) and splices the result back in, in place, exactly as it would have rendered before this plugin existed. It also records each _referenced_ definition's source line, which `footnote_open` and `footnote_block_open` overrides use to stamp `data-source-line` on the `<li>` and the `<section class="footnotes">`: without it, the footnotes section is invisible to `blockMarkdown`, `anchors()`, and the context menu's `[data-source-line]` lookup in `src/webview/main.ts`, none of which needed to change once the attribute was there. `footnote_caption` is also overridden, to number a repeated reference `[1]` on every occurrence the way GitHub does rather than the plugin's own `[1]`/`[1:1]`. The plugin's separate `^[inline footnote]` shorthand is disabled outright (`md.inline.ruler.disable('footnote_inline')`): it is not documented anywhere in this repo, and `^[` is common in prose about regular expressions.

### Math (KaTeX)

Math rendering mirrors how Mermaid diagrams are handled, so the same DOMPurify-adjacent path is reused rather than adding a second one. `render.ts` parses `$...$` and `$$...$$` with `markdown-it-texmath` (dollars delimiters, gated on `markcopy.math`) and emits inert placeholders instead of rendering KaTeX on the host: `<span class="mc-math" data-display="0">TeX</span>` for inline math and `<div class="mc-math" data-display="1" data-source-line="N">TeX</div>` for display math, with the raw TeX also stashed in `data-tex` for the copy actions. The webview's `renderKatex()` (in `src/webview/main.ts`) finds every `.mc-math` placeholder **after** DOMPurify has already sanitized the rendered HTML and calls `katex.render()` on its stored TeX, exactly mirroring the Mermaid placeholder-then-upgrade pattern. Keeping KaTeX's own markup out of the sanitizer path avoids DOMPurify stripping or fighting KaTeX's generated `<span>` soup.

Right-clicking an equation offers top-level **Copy Equation** (PNG, via `html-to-image`, reusing the existing `copyPng` path) and **Copy as > LaTeX** (rewraps the `data-tex` value in `$...$` or `$$...$$` depending on `data-display`). The "Markdown" row under Copy as, for either a selection or a block, also restores the original LaTeX for any equation in scope via a Turndown rule, instead of serializing the rendered KaTeX markup.

### Auto-open preview

`extension.ts` listens on `vscode.window.onDidChangeActiveTextEditor` and asks `autoPreviewKind` (in `preview-utils.ts`) how, or whether, to preview it. It requires the `markcopy.autoPreview` setting to be on, the focused document to be Markdown, CSV or TSV on an on-disk file (`scheme === 'file'`, so untitled buffers never trigger it), and the document to be absent from `dismissedPreviews`, a `Set` the extension keeps for documents whose preview the reader has turned away from this session.

What it then does depends on whether a side panel is open. Normally it is `showRendered`, the same call the **Show Preview** button makes: the tab swaps to the rendered document in the group it is already in. It used to open the side panel `Beside` instead, and the split that produced was the thing readers actually noticed about auto-preview. But a reader who has run `markcopy.openPreview` asked for two columns, so while `side` exists auto-preview keeps that bargain and retargets the panel exactly as it always did, rather than swapping the tab. Swapping under an open panel would be the worst of both: the panel left rendering a document no longer open anywhere, the file just clicked turned into a preview in the other column, and no source editor left on screen.

Four guards keep an automatic swap from being rude, and they are stricter than the button's. `swappable` refuses the swap entirely, rather than merely declining to close the source tab the way `closeStaleEditor` does, when any of them says the reader is working in the text:

- The document `isDirty`. Read off the document rather than off its tab, because a tab only reports `isDirty` for a plain text editor in the active group, which missed a dirty document open in a diff or in an unfocused group.
- Its tab in the active group `isPinned`. Pinning is the reader saying "keep this one", and a pinned source that flipped to the preview every time it was clicked would be unusable.
- The focused tab is a `TabInputTextDiff` with the document on either side. Clicking a modified `.md` in the Source Control list focuses the working-tree side of a diff, and a preview that opened over it and took the focus made reviewing a Markdown change impossible at the default setting.
- The cursor is not at the top of the file. Something put it there: a Find-in-Files hit, a `Ctrl+P` with a `:120`, a go-to-definition. Each opened the editor _at a line_, and the swap closes that editor before its visible range can sync to the preview, so the line would simply be lost. Scrolling the preview to that line instead was the other option and was rejected: someone who follows a search hit into a Markdown file usually means to edit it, and a read view at roughly the right place is not what they asked for. The price is that a text editor VS Code restores with a saved cursor position does not swap either, which is the conservative side of the trade and leaves the reader with what they had open.

The buttons still work on those tabs, because a click is an answer and a focus change is not. `markcopy.openSource` records the dismissal, so asking for the text keeps you in it; `markcopy.openRendered` and `markcopy.openPreview` clear it again. `panel.onDidDispose` records one too, but only for the side panel: a preview that is an editor tab takes the document with it when it closes, so there is no focused editor left for auto-preview to answer.

`showRendered` carries two guards of its own, both learned from the LaTeX path next door. `openingRendered` stakes a synchronous claim before the asynchronous `vscode.openWith`, so a burst of focus changes over one document collapses to a single preview instead of a stack of retained-context webviews. And it closes the source tab only once a custom tab on that document is actually there: `previewKind` answers for a language id as well as an extension, and VS Code's own Markdown grammar claims files the `package.json` selector does not, so `openWith` can decline the viewType and hand back the plain text editor. Closing regardless took the file's only tab away as it was opened.

Because the extension activates on `onLanguage:` events (`markdown`, `mdx`, `csv`, `tsv`, and `latex`; the binary previews activate through their custom editors), a Markdown editor that's already active when the extension activates never fires `onDidChangeActiveTextEditor`, since that event only fires on a _change_ of focus. `activate()` runs the same auto-preview check once more directly, against `vscode.window.activeTextEditor`, so the file that triggered activation gets a preview too, not just the next file you switch to.

A `.tex` file gets the same bargain, `markcopy.autoPreview` on by default and dismissal for the session once closed, but it keeps the `Beside` layout the others gave up. Its preview is a compiled PDF rather than a view of the text, so swapping the tab to it would leave the author nothing to edit, which is the one case where a split is the point rather than the problem. It also arrives by a different route: `TexEditorProvider` is a `CustomTextEditorProvider`, so its preview only exists as a tab bound to one document for life, the same as a Markdown or CSV tab (see [The two preview surfaces](#the-two-preview-surfaces)). So `onDidChangeActiveTextEditor`'s handler branches on `isTexDocument` before it ever reaches `autoPreviewKind`, and for a `.tex` file it instead calls `openTexPreview`, which opens (or reveals) the LaTeX custom-editor tab beside the source with `vscode.openWith` and `{ viewColumn: ViewColumn.Beside, preserveFocus }`. `preserveFocus` is `true` on this automatic path for the same reason it matters for Markdown: the reader is typing in the source, and yanking the cursor into a preview they did not ask for would be worse than not showing one.

Calling it on every focus change is only safe because `openTexPreview` guards it twice, and both guards are load-bearing. `texPanelFor` (exported by `texEditor.ts` off the `active` registry) catches the case where a panel for this document is already open, and leaves it exactly where it is on the automatic path rather than revealing it, since pulling a tab into view while someone is typing is its own kind of rude. That check alone is not enough, though, because it can only see panels that have finished resolving and `vscode.openWith` is asynchronous. Restoring a folder full of editors churns the active editor several times in a row with nothing awaited in between, so every pass in that burst sees "no panel yet" and starts another open. A second `Set`, `openingTex`, stakes a synchronous claim keyed by document URI for exactly that window, and is released when the command settles, on failure as well as success, so one refused open cannot wedge a document out of previewing for the rest of the session.

This is not a hypothetical. Without the synchronous claim, a burst of eight requests produced eight panels, each a full pdf.js webview with its own compile session and listeners, which is enough to abort the extension host. The launch configuration opens this repository as the dev host's own workspace, so `sample.tex` restoring alongside the other fixtures was the reproduction. `test-integration/customEditors.test.ts` pins it by firing the burst without awaiting, which is the whole point: awaiting between calls hides the bug completely.

Dismissal works the same way as Markdown's, but through a different hook: `TexEditorProvider` takes an `onDismiss` callback in its constructor, called when its `resolveCustomTextEditor` panel disposes, so a closed LaTeX preview does not spring back open the next time its document gets focus. `onDismiss` is injected from `extension.ts` rather than imported by `texEditor.ts`, so that `texEditor.ts` does not need to import `extension.ts` and close a cycle back into it; that is the same constructor-injection arrangement `xlsxEditor.ts` uses for its own `ExportPdf` callback, for the same reason.

Retargeting an existing preview to a different document is careful not to grow a third editor column. If VS Code opened the newly-focused Markdown file as a tab in the preview panel's own column (which it does when that column was the active group), `openPreview` moves that editor back to `ViewColumn.One` before retargeting. And revealing the retargeted preview always uses the panel's own existing `viewColumn`, never `ViewColumn.Beside`, so retargeting can't itself spawn a new column.

## Context menu

The Markdown and PDF webviews build their right-click menu the same way. `src/webview/menu.ts` is a shared engine, exporting `MenuEntry`, `MenuController`, and `createMenu(root)`; `main.ts` and `pdf.ts` each call it with a tree of entries built for whatever the user clicked. Neither webview implements its own `showMenu` anymore: that logic (positioning, event handling, submenu panels, keyboard navigation) lives once in `menu.ts`, and `main.ts` / `pdf.ts` are reduced to building `MenuEntry[]` trees and wiring `run()` callbacks to the existing copy and settings functions. This replaced two near-duplicate `showMenu` implementations that used to live one in each file.

A `MenuEntry` is one of six kinds:

- `item`: a plain clickable action (`label`, `run`).
- `submenu`: a nested panel (`label`, `entries`), for example "Copy as" or "Preferences".
- `label`: a non-interactive group heading, used to split "Copy as" into per-context sections (for example `SELECTION` and `TABLE`) when more than one element is in scope.
- `divider`: a horizontal rule.
- `radio`: a mutually exclusive checked option (the Theme entries).
- `checkbox`: an independently toggled option (Sync scroll, Auto-open preview, Math, Footnotes).

`createMenu(root)` renders the root panel into the host page's `#mc-menu` div and appends nested submenu panels to `<body>` (class `mc-menu mc-menu--sub`) as they're opened, one panel per depth. `MenuController` tracks which panel is open at which depth and drives keyboard navigation: opening the menu focuses its first row (so the arrow keys work without tabbing in first, and because focusing a non-editable element leaves the document's text selection intact for the `Copy Selection` actions), ArrowUp/ArrowDown move within a panel, ArrowRight or Enter opens a highlighted submenu, ArrowLeft or Escape steps back out to the parent panel (or closes the menu entirely from the root), and Enter/Space activates the highlighted item, radio, or checkbox. New CSS in `media/preview.css` (`.mc-menu--sub`, `.mc-menu-item--submenu`, `.mc-menu-arrow`) styles the nested panels and the arrow glyph marking a row as a submenu. `tests/menu.test.ts` unit-tests the engine.

Three details of the engine exist because submenu panels are siblings of the root rather than descendants of the row that opened them. Nothing connects a row to its panel structurally, so `openSubmenu` names each end for the other (`aria-controls` on the row, `aria-labelledby` on the panel, both cleared on close) to keep the accessibility tree honest about where "Copy as, submenu, expanded" leads. The pointer path from a row to its panel is diagonal and clips the rows in between, so hovering a non-submenu row only _queues_ the dismissal of anything deeper, on a 150ms timer that reaching any panel cancels. And because panel chrome (padding, dividers, group headings) has no click behavior of its own, each panel swallows clicks that reach it, since the document-level handler both webviews use to close the menu cannot otherwise tell a stray click inside the menu from a click outside it.

`main.ts`'s `buildMenu()` builds the Markdown preview's tree: a top-level `Copy <Noun>` item for the most specific element in scope (precedence Link > Selection > Code > a grid cell whose own text is a recognized email address or URL > Table > Diagram > Equation > Block, with an ordinary grid cell ranking behind Table) in that element's primary format, a `Copy as` submenu with every remaining format for the element(s) in scope, `Copy Whole Document`, `Save as PDF…`, `Save as Word…`, `Save as PowerPoint…`, and a `Preferences` submenu (a nested `Theme` submenu, then the Sync scroll / Auto-open preview / Math / Footnotes checkboxes and `MarkCopy Settings…`). `pdf.ts`'s equivalent builds `Copy Selection` (only when text is selected), `Copy Page N as PNG` (only over a rendered page), a `Copy as` submenu (`Page N Text`, `All Text`), `Add Comment Here` (only over a page), and its own `Preferences` submenu (the Hand/Pointer tool toggle, the Dark/Light Pages toggle, and a nested `Theme` submenu).

The net effect is a much shorter top level: the Markdown preview's was up to 19 rows (16 even on a plain paragraph, since an 11-row settings block was appended unconditionally) and is now seven on a plain paragraph (Copy Block, Copy as, the four document actions, and Preferences); the PDF viewer's was up to 13 and is now at most 6. No action was removed, every one of them just moved one level down into `Copy as` or `Preferences`.

It does not handle `revealLine`, `editCell`, or `gridOp`: a workbook has no visible text editor to reveal into, and no addressable lines to write a cell or a row back to.

The PowerPoint preview follows the same pattern one step further: `PptxEditorProvider` posts `render` with `kind: 'pptx'`, `source: ''`, `docVersion: -1`, and `supportsSync: false` (there is no `TextDocument` behind a deck at all, not even the workbook's binary-but-openable kind), and handles `ready`, `pdfHtml`, `docxXhtml`, `pptxXhtml`, `openLink`, `updateSetting`, `openSettings`, and `toast`. It adds nothing of its own, unlike the spreadsheet preview's `selectSheet`, because a deck has no per-slide state for the webview to ask the host to switch: every slide is already on screen at once (see [PowerPoint preview](#powerpoint-preview)).

The PDF preview uses its own message protocol: the webview posts `ready`, and the host replies with `load` (`data`: the file bytes as a base64 string, `workerSrc`: the pdf.js worker URI, `comments`: the parsed sidecar comments array). The bytes are base64-encoded because a `Uint8Array` does not survive `postMessage` serialization to the webview; `pdf.ts` decodes it back to a `Uint8Array` before handing it to pdf.js. Most copy actions run entirely in the webview with no further host round-trip. Two messages are the exception. Comments: the webview posts `saveComments` (`comments`: the full current array) back to the host whenever a pin is added, edited, or deleted, and `pdfEditor.ts` writes that array to the sidecar JSON file, deleting the file when the array is empty. The Preferences > Theme submenu: picking a theme posts `updateSetting` (`key`, `value`) so the host persists `markcopy.theme`, written the same scope-aware way as the Markdown preview (a WorkspaceFolder or Workspace override if present, else Global), so the setting is shared with the Markdown preview rather than being PDF-only.

The LaTeX preview runs through the identical webview code (see [LaTeX preview](#latex-preview)) and reuses this same protocol, extended with two message types of its own. Host to webview: `texState` (`state`, `text`, `detail`, `action`) reports compile status independently of `load`, which the LaTeX preview also receives, once per successful compile rather than the once-per-panel a plain PDF gets. Webview to host: `texRecompile` (no payload), posted both by the overlay's own action button and by the "Recompile LaTeX" context-menu entry, asking the host to run the panel's `CompileSession.run()` again. The `markcopy.recompileTex` command reaches the same method a different way, straight from the host side rather than through the webview: `recompileActiveTex()` (`src/texEditor.ts`) finds whichever LaTeX panel is focused and calls `session.run()` on it directly.

## CSV editing

The CSV grid is editable, and the design principle is that **the document is the only state**. The grid never mutates itself on commit: `src/webview/csvEdit.ts` posts an `editCell` message and waits. The host rewrites the field, VS Code fires `onDidChangeTextDocument`, and the preview re-renders from the new text. Three things fall out of that for free: the file and the grid can never disagree, `Ctrl+Z` works because the change is an ordinary `WorkspaceEdit`, and an edit made in the text editor shows up in the grid identically to one made in the grid.

Writing the value back is the part worth care. The naive approach, reserialising the whole record from its parsed cells, would silently reformat the rest of the row: quoting we would not have chosen (`"unnecessarily quoted"`) would be dropped, and a hand-maintained file would churn on every edit. So the parser records a `FieldSpan` (`start`/`end` offsets into the original text) for every field alongside its value, and `cellEdit` returns a replacement for **that one span**. Every other byte in the file, quoting and line endings included, is untouched. `formatField` adds quotes back only when the new value actually needs them, and is the exact inverse of what the parser reads, so a value round-trips unchanged.

Two guards keep an edit from landing in the wrong place:

- **Records are addressed by the source line they start on**, not by a rendered row index. Row indices shift when `markcopy.csv.headerRow` or `maxRows` changes; a starting line is stable, and no two records share one.
- **The render message carries `docVersion`**, the version the grid was drawn from, which it echoes back with the edit. The host accepts it while those line numbers still mean what they meant: either the version still matches, or nothing has added or removed a line since (`lineCountVersion` records when that last happened). A cell edit rewrites a field inside a single line, so line numbers survive one. Requiring an exact match instead would swallow edits, because MarkCopy's own writeback bumps the version and the grid only learns the new one once the re-render reaches it, so typing quickly across two cells would lose the second. An edit that does move lines (committing a value containing a newline) fails the check and is refused; the re-render already in flight carries the truth.

A ragged row (fewer fields than the grid is wide) is grown in place: `cellEdit` appends just enough delimiters to reach the edited column. Because each render replaces the grid wholesale, the focused cell is remembered as a (record line, column) pair and re-seated after the re-render a commit triggers, so typing down a column is not interrupted.

Whole rows and columns take the same path, as a `gridOp` message: `gridEdits` in `src/csv.ts` turns one of six operations into a list of span replacements, and the host applies them as a single `WorkspaceEdit`, so a column that touches every row of a file is still one change and one `Ctrl+Z`. Three rules make the result predictable:

- **A row operation addresses one record**, so a row holding a quoted newline is one row here too, and a delete takes the line terminator that closes the record with it rather than leaving a blank line behind. The last row of a file that does not end in a newline has none of its own, so the one in front of it goes instead.
- **An inserted row is as wide as the row it lands next to**, not as wide as the widest row in the file. A ragged document stays exactly as ragged as it was, and the grid never gains a column because a blank row was added to it.
- **A column operation deliberately reaches records the grid never rendered**, including everything past `markcopy.csv.maxRows`. A column belongs to the file rather than to the window onto it; shifting only the visible rows would shear the file in half at the truncation point. A record takes part only if it actually reaches the addressed column: a row that stops short of it has no field to shift and none next to the new one, so it keeps its bytes.

That last rule is also why a column operation is not bounded by anything the reader can see, and a large file can produce a replacement per record. Past `MAX_GRANULAR_EDITS` ranges the host applies them itself (`applyCsvEdits`) and sends one whole-document replacement instead. The text is identical either way and it is still one undo stop; what it gives up is a fine-grained diff, on files too large to read one from.

The menu that sends these is built over whatever was right-clicked, the row-number gutter included, and focus is parked (`parkFocus`) before the message goes out, on the same square the reader was already standing on. The grid moves under them rather than the other way round: after an insert above they are on the new blank row, and after a delete on whatever has slid up into its place. When the square itself is gone rather than merely refilled, which is what deleting the last row or the last column does, the nearest surviving cell takes it, so the reader is never left outside the grid with the arrow keys dead.

## Clipboard

This is the core of MarkCopy, and the reason for the host/webview split.

### Why writing happens in the webview

`vscode.env.clipboard.writeText` is text-only; there is no rich-HTML API on the extension host. Rich copy therefore has to run in the webview, which is a browser context with a full Clipboard API.

### Why the `copy`-event trick, not `navigator.clipboard.write`

The async Clipboard API (`navigator.clipboard.write` with a `ClipboardItem`) can be blocked inside the VS Code webview iframe by its Permissions-Policy on some versions and platforms. The reliable path is a synchronous `copy`-event handler plus `document.execCommand('copy')`:

```js
function writeClipboard(html, plain) {
  const onCopy = (e) => {
    if (html) e.clipboardData.setData('text/html', html);
    e.clipboardData.setData('text/plain', plain);
    e.preventDefault();
  };
  document.addEventListener('copy', onCopy);
  const ok = document.execCommand('copy');
  document.removeEventListener('copy', onCopy);
  if (!ok) navigator.clipboard?.writeText(plain); // last-ditch fallback
}
```

Every rich or text copy writes `text/plain` as well, so targets that cannot take HTML still receive content.

### Why styles are inlined

Gmail and Outlook strip `<style>` blocks and external CSS, honoring only inline `style` attributes. `inlineStyledHtml()` clones the target node, walks every element, and copies a whitelist of computed properties (font, color, background, borders, padding, margin, alignment, list style, white-space) onto inline styles. That is what makes a pasted table or heading keep its look in an email.

Before reading computed styles, the source is briefly tagged with an `mc-force-light` class that overrides the palette to light values. This keeps copies dark-on-light even when the preview is displayed in a dark theme (a dark preview would otherwise inline light text that pastes invisibly into a white document). The class is added and removed synchronously within the copy call, so the on-screen preview never repaints.

### PNG copy

`copyPng()` uses `html-to-image`'s `toBlob()` at 2x pixel ratio, then writes an `image/png` `ClipboardItem`. This is the one place the async Clipboard API is used, because image writes are not expressible through the `copy`-event path. If the environment blocks it, the user sees a toast rather than a silent failure. The same path handles top-level **Copy Equation**; rasterizing a KaTeX equation additionally requires `html-to-image` to fetch KaTeX's web fonts, which is why the CSP has a same-origin `connect-src` (see [Content Security Policy](#content-security-policy)).

## PDF export

**Save as PDF** reuses the on-screen render rather than re-rendering the document: the preview already holds fully upgraded KaTeX HTML, Mermaid SVGs, and highlighted code, so `exportPdf()` clones `#content`, prepares the clone, and posts its `innerHTML` to the host as a `pdfHtml` message. Preparing the clone does three things the raw DOM can't be shipped without:

- **Relight Mermaid.** Mermaid bakes theme colors into each SVG at render time (the same reason the host re-renders diagrams on a theme change, see [Theming](#theming)), so a diagram rendered for a dark preview is dark-filled with light labels: invisible black boxes on the forced-light PDF page. `relightMermaid()` re-renders every `.mc-mermaid` from the source stashed in `data-mermaid-src` at render time, with `theme: 'default'`, then restores the on-screen config via `initMermaid()`. Text, KaTeX, and code need no such treatment: they inherit color from CSS, which the PDF page forces light.
- **Inline local images.** `inlineImages()` replaces every webview-hosted `src` with a `data:` URI so the images survive on a plain `file://` page outside the webview; remote `https:` and already-inlined `data:` sources are left alone.
- **Strip `data-source-line`.** The scroll-sync attributes are preview-only noise in an exported document.

The host (`exportPdf` in `src/extension.ts`) wraps the markup in a standalone HTML page carrying `preview.css` and the KaTeX stylesheet with its fonts inlined (`buildPdfPage` in `src/pdfExport.ts`), forces the light palette for a clean printout, and renders it to the file the user picked in a save dialog. The rendering is done by a headless Chromium-family browser (`--headless --print-to-pdf`), located by `findBrowser()`: the `markcopy.pdf.browserPath` setting if set, else the usual Edge/Chrome/Chromium/Brave install locations for the platform. The page and the browser's throwaway profile both live in one `mkdtemp` directory, deleted however the render ends, and the finished PDF is handed to the OS with `openExternal`.

Three details of that command line matter (`printArgs`):

- **`--no-pdf-header-footer` and `--print-to-pdf-no-header`** (the current and older spellings; Chromium ignores switches it does not recognize). Without them the output carries the furniture the interactive print dialog adds by default: the document title across the top of every page and the `file://…` URL across the bottom.
- **`--user-data-dir`** pointed at a fresh directory. Without it, launching a browser the user already has open just hands the URL to the running process, which prints nothing at all.
- **`--headless`, not `--headless=new`.** Recent Chromium maps the bare flag to the new mode anyway, while builds predating `=new` would fail to parse it and open a visible window instead of printing.

A browser that cannot open the page still exits 0 and still writes a PDF (of its error page), so `renderPdf()` treats a suspiciously small output file as a failure rather than trusting the exit code. If no browser is found, or a render fails, `printViaBrowser()` is the fallback: it writes the page to the extension's `globalStorageUri` and opens it in the default browser with a `window.print()` on load, which is what the export used to do for everyone. Because `globalStorageUri` uses the `vscode-userdata:` scheme, which the OS shell has no handler for, the file is reopened as a plain `file:` URI (`vscode.Uri.file(fileUri.fsPath)`) before `openExternal`, or the browser hand-off fails.

### Print stylesheet

`pdfCss()` layers print rules over `preview.css`. Most of them undo something the on-screen preview needs and paper does not, and the two that matter most are the ones a naive print stylesheet gets wrong:

- **Only atomic things forbid an internal break.** A blanket `pre, table { break-inside: avoid }` cannot be honoured for a block taller than a page; a browser that cannot honour it pushes the block onto a fresh page anyway and leaves the rest of the previous page blank. Tall blocks are allowed to split (`break-inside: auto`) and `thead { display: table-header-group }` repeats a table's header on every page it spans, so a long table reads correctly wherever it breaks. `break-inside: avoid` is kept only for images, diagrams, equations, and table rows.
- **Nothing may rely on scrolling.** `overflow: auto` on a `pre` or a table is a horizontal scrollbar on screen and a silent clip in print, losing whatever does not fit the page width. Both become `overflow: visible` with wrapping (`white-space: pre-wrap`, `overflow-wrap: anywhere`). Relatedly, the export page's `<body>` deliberately omits `data-mc-kind`: a CSV preview uses it to become a viewport-tall flex column that scrolls internally, and on paper that would clip everything past the first page's worth of rows instead of paginating.

`print-color-adjust: exact` is also set, because Chromium otherwise drops background colours from a print and flattens every code block, table header, and blockquote to plain white.

## OOXML container

An `.xlsx`, a `.docx`, and a `.pptx` are all the same thing underneath: a zip of XML parts (the [Open Packaging Conventions](https://en.wikipedia.org/wiki/Open_Packaging_Conventions)). `src/ooxml/` is what all three need and none of them owns, and it did not start that way: `zip.ts` and `xml.ts` used to live in `src/xlsx/`, since the workbook reader was the only feature that needed them. They moved when the deck reader arrived and needed the same container and the same SAX walker, and the signal that they belonged somewhere neutral rather than being copied a second time had already shown up before that: `src/docx/parse.ts` was reaching across into `src/xlsx/xml.ts` for `walkXml`, a writer depending on a reader's internals for a piece of plumbing neither format actually owns.

- **`zip.ts`** unpacks the OPC container: `openZip()` refuses a file that is too large before inflating anything, refuses a declared entry size or a running total past its limits mid-unzip, and refuses whatever `fflate`'s `unzipSync` cannot parse, all before a single tag is read. It also defines `OpcError`, the one refusal type for a package MarkCopy will not or cannot read. One class serves every format on purpose: each feature re-exports it under the noun its own callers use (`export { OpcError as WorkbookError }` in `src/xlsx/index.ts`, `export { OpcError as DeckError }` in `src/pptx/read/index.ts`), so `err instanceof WorkbookError` at the top of the spreadsheet preview and `err instanceof DeckError` at the top of the deck preview each read the way they always did, and `openZip`'s `noun` option makes its own messages say "presentation" where a deck is what failed and "workbook" where one wasn't.
- **`xml.ts`** is the saxes pull-parsing layer (`walkXml`, `attr`, `boolAttr`, `intAttr`) every reader and both writers' XHTML parser walk XML with. Resolving only the five predefined XML entities and expanding nothing from a DTD is what keeps a billion-laughs or XXE payload inert, and living in one place means that property cannot go missing from a copy.
- **`rels.ts`** reads one `.rels` relationship part (`readRels`; `readExternalRels` is the one deliberate exception to the refusal below, for a Word hyperlink's target, which is only ever shown as a link and never fetched) and resolves a relationship's target against the part that declared it (`resolveTarget`, `partForRels`), including refusing an `External` relationship outright, since following one would turn opening a file into a network fetch. The workbook reader, the deck reader, and the deck writer's package assembly all need exactly this and nothing format-specific.
- **`write.ts`** holds the XML escaping and invalid-character stripping the two writers need (`escapeXml`, `escapeAttr`, `stripInvalidXml`, `XML_DECL`): Word and PowerPoint reject a malformed part for the same reason, so the rule is not either writer's to own. `src/docx/ooxml.ts` re-exports these rather than defining its own, so nothing inside `src/docx` had to know they moved out.
- **`xnode.ts`** is the small in-memory XML tree (`parseXml`, `child`, `children`, `findDeep`, `findAll`) the deck and document readers build once per part, where the deeply irregular nesting of a slide or a Word body is far easier to walk with recursion than to track in a streaming pass. It started life in `src/pptx/read/` and moved here when the Word reader needed it.
- **`media.ts`** turns an image part into a `data:` URI (`imageDataUri`) against one byte budget per file, encoding each distinct part once and refusing formats a browser cannot show (EMF, WMF). The deck and document readers both deliver images through it.
- **`xhtml.ts`** parses the serialized XHTML the webview hands the host (`parseXhtml`) into the small element tree both writers build their output from. It stays out of the streaming reader path deliberately: a worksheet's `<sheetData>` can run to hundreds of megabytes inflated, where a rendered preview is capped by what a person is willing to read, so building a full tree here is safe in a way it would not be for `xml.ts`'s callers.

See [Word export](#word-export) and [PowerPoint export](#powerpoint-export) for the writers built on this, and [Spreadsheet preview](#spreadsheet-preview) and [PowerPoint preview](#powerpoint-preview) for the readers.

## Word export

**Save as Word** answers a different question from Save as PDF, and the difference decides the whole design. A PDF is a picture of a page: it keeps the layout and the images, and a screen reader is left inferring the reading order from where the ink fell. A `.docx` keeps the structure, and structure is what assistive software actually reads. So where the PDF path ships the preview's _styling_ (inline styles, the stylesheet, forced-light colors), this one ships its _semantics_ and throws the styling away.

`exportDocx()` in `src/webview/main.ts` clones `#content` and posts a `docxXhtml` message, the same shape as `pdfHtml`, with four differences forced by the target:

- **The clone is staged in the document, not detached.** Rasterizing needs layout. The stage is fixed at `left:-10000px` and 624px wide, which is the Word text column (6.5in at 96dpi, `CONTENT_WIDTH_PX` in `src/docx/media.ts`), so a diagram is drawn at the size it will occupy on the page rather than at the preview's width.
- **Mermaid and KaTeX are rasterized, with their source as alt text.** Word can render neither. `rasterizeFigures()` replaces each `.mc-mermaid` and `.mc-math` with an `<img>` whose `alt` is the `data-mermaid-src` or `data-tex` it was rendered from, drawn at 2x and pinned back to its CSS size with `width`/`height` so the host lays it out correctly. A picture of an equation is silent; a picture described by `E = mc^2` is not.
- **Images end up as png/jpeg/gif.** Those are the formats a `.docx` can hold as a part. `inlineImages()` runs as it does for PDF, then `toEmbeddableImages()` redraws anything else (SVG, WebP, AVIF) through a canvas. Word does take SVG, but only alongside a raster fallback part, which is a lot of package machinery for something the browser rasterizes for free.
- **It is serialized with `XMLSerializer`, not `innerHTML`.** The host parses with saxes, which is a strict XML parser and rejects `<img src="x">` unclosed at the first image.

The one piece of styling that does travel is syntax color: highlight.js colors code through the stylesheet, which does not survive serialization, so `inlineCodeColors()` writes each token's computed color into its `style` attribute and `build.ts` reads it back off.

The host (`exportDocx` in `src/extension.ts`) is short, because there is no browser to find and no subprocess to babysit: `htmlToDocx()` returns the bytes and they are written to the path the user picked. `parseXhtml()` (`src/ooxml/xhtml.ts`, see [OOXML container](#ooxml-container)) builds the element tree first, over the same `walkXml` that keeps billion-laughs and XXE inert for the readers too, and `src/docx/` does the rest in three passes: `build.ts` walks that tree into the body of `word/document.xml` while collecting media, relationships and numbering instances, `media.ts` decodes each data URI and reads its intrinsic size straight out of the PNG/JPEG/GIF header, and `package.ts` assembles the OPC container with `fflate`'s `zipSync` (already a dependency for _reading_ `.xlsx`; an OOXML package is the same container in the other direction, so the export adds none).

**The mappings that matter are the accessibility ones**, and they are the reason `build.ts` is the size it is:

- `h1`-`h6` become the built-in `Heading1`-`Heading6` styles. "Built-in" is load-bearing: the `w:name` must be Word's own lowercase name (`heading 2`, not `Heading 2`) or Word treats the style as a look-alike, and the outline level that drives the Navigation Pane and heading-to-heading screen reader movement never appears.
- A table's header row gets `<w:tblHeader/>`, which marks it as the row that labels the columns. A row inside `<thead>` counts, and so does a row that is all `<th>`, which is how the CSV grid marks one.
- Images carry `descr` on both `wp:docPr` and `pic:cNvPr`; different readers have historically consulted different ones.
- Lists get real numbering, one `<w:num>` instance per list element, with a `startOverride` so a second ordered list restarts at 1 instead of continuing the first. Sharing one instance across the document is the obvious approach and is wrong twice: continuous numbering across unrelated lists, and no way to put a decimal level under a bullet one.
- Headings with an `id` (markdown-it-anchor mints them) get a bookmark, so a table of contents links inside the document rather than at a URL that does not exist.

What the converter cannot do is invent alt text. `![](chart.png)` is the norm in Markdown and is exactly what makes a document stop being audible, so `build.ts` counts undescribed images and `reportSummary()` turns the count into the message the host shows after the export. Reporting it is the whole answer: guessing would be worse than silence.

## PowerPoint export

**Save as PowerPoint** asks the same question Save as Word does, and answers it the same way: a `.pptx` should carry structure, not a picture of one. `exportPptx()` in `src/webview/main.ts` clones `#content` and posts a `pptxXhtml` message, the same shape as `docxXhtml`, through the identical staging, rasterizing, and serialization steps ([Word export](#word-export) above covers all four). The seam past that point, `htmlToPptx()` in `src/pptxExport.ts`, is where the format actually diverges: a `.docx` page is one continuous flow that reflows around whatever is on it, and a `.pptx` slide is a fixed canvas, so before anything can be turned into DrawingML something first has to decide where one slide ends and the next begins.

`src/pptx/write/build.ts`'s `segmentSlides()` is that decision. A slide boundary is a thematic break (`---`) **or** an `<h1>` / `<h2>`, which then becomes the slide's title, and it is deliberately both rather than one falling back to the other:

- Content before the first boundary is its own slide: a title slide when it is only a heading, an ordinary one otherwise. Consecutive boundaries do not mint an empty slide between them.
- A deck written for a tool like Marp splits identically either way, because its headings already sit one to a section, so taking both boundaries costs that case nothing.
- Falling back to headings only when the document has no `---` at all was the first draft, on the reasoning that an author who writes `---` means it. What that missed is that the author is not the only thing that writes one: `markdown-it-footnote` emits an `<hr class="footnotes-sep">` above the footnote list, so a single footnote anywhere in an otherwise heading-only document silently collapsed a six-heading file into two slides. A rule a stray `<hr>` can quietly wreck is the wrong rule.

Layout inside a slide reuses rather than reinvents: `build.ts` imports `cssColor` from `src/docx/build.ts` and `decodeImage` / `EMU_PER_PX` from `src/docx/media.ts`, so color parsing and image decoding are not a third implementation. Shapes are laid out top to bottom with a running cursor in EMU; when that cursor runs past the slide's bottom edge, the slide is marked overflowed rather than split. Splitting one into two would scramble a deliberate build (a slide the author paced for a click-through animation, say), so overflow is the author's to fix, the same as a table too wide for a PDF page is table's problem, not the export's to solve by guessing where the author would have wanted the cut.

`src/pptx/write/package.ts` assembles the OPC container, using the same `escapeXml` / `escapeAttr` / `XML_DECL` from `src/ooxml/write.ts` the docx writer re-exports. The design doc (`docs/PPTX-DESIGN.md`) calls out why this half is stricter than the docx writer: Word tolerates a part it does not recognize, but PowerPoint does not tolerate one it expects and does not find, a missing master, a `clrMap`-less master, a relationship id nothing resolves, so `package.ts` writes exactly the parts a presentation needs and every one of those, rather than the minimal set that merely opens.

As with `docx`'s alt-text count, what the converter cannot invent it counts instead: `reportSummary()` in `src/pptxExport.ts` turns `imagesMissingAlt`, `imagesSkipped`, and `overflowed` into the one-line warning the host shows after the export (`MarkCopy: exported deck.pptx, but 3 images without alt text (a screen reader will skip past them); 1 slide likely run past the bottom edge.`), missing alt text leading for the same reason it leads for Word, since it is the one defect that is still fixable in the Markdown source in seconds.

## PDF preview

`.pdf` files are handled by `PdfEditorProvider`, a `CustomReadonlyEditorProvider` registered for the `markcopy.pdfPreview` view type (contributed with `priority: default`, since VS Code has no built-in PDF viewer). On open, the provider reads the file with `workspace.fs.readFile` and, once the webview posts `ready`, sends the bytes, the worker URI, and any saved comments (read from the sidecar JSON file) in a `load` message. Nothing is fetched over the network.

In the webview, `src/webview/pdf.ts` builds one placeholder `<div class="mc-page">` per page up front (sized from the page's scale-1 viewport) but does not rasterise anything yet; an `IntersectionObserver` (`rootMargin: '150% 0px'`) rasterises a page's canvas and text layer only once it nears the viewport, and tears both down again once it scrolls away, so memory use stays bounded regardless of how many pages the PDF has. Each page's canvas is rendered above display resolution (at least 2x, or the device pixel ratio if higher) so text stays sharp, clamped to a roughly 16.7-million-pixel budget (`MAX_CANVAS_PIXELS`) so the canvas itself never grows large enough to trigger the browser's own blur-inducing downscale. A pdf.js `TextLayer` of transparent, selectable spans is rendered over each canvas from the same `getTextContent()` call used for the copy actions, so highlighting text on a page is real text selection, not a canvas artifact.

Starting the pdf.js worker takes an extra step: the worker script can't be constructed directly from its `webview-resource:` URI, since that origin differs from the webview document's `vscode-webview://` origin and `new Worker(workerSrc)` throws a `SecurityError`. Instead, `pdf.ts` `fetch`es the worker script and wraps it in a same-origin `Blob`, then starts `new Worker(blobUrl, { type: 'module' })` from that. The PDF webview's CSP adds `worker-src ${cspSource} blob:` and `connect-src ${cspSource} blob: data:` to allow the fetch and the blob worker. Any load failure (bad bytes, worker error) is caught by `error` / `unhandledrejection` handlers and shown as a visible message in the panel instead of a silent blank page.

Zoom is stepped through fixed preset levels (50, 67, 80, 90, 100, 110, 125, 150, 175, 200, 250, 300, 400 percent) rather than continuous, so the label and re-raster targets stay predictable. A floating toolbar (bottom-right) has minus/plus buttons and a percentage that resets to 100 percent on click; Ctrl and plus / Ctrl and minus / Ctrl and 0, and Ctrl plus the mouse wheel do the same. Changing the zoom level immediately resizes every page's placeholder (so scroll position and layout stay correct) but debounces the actual re-raster by 120ms after the last step, so scrolling quickly through zoom levels doesn't rasterise every intermediate one.

`scale`, not an index into the preset list, is the source of truth, because fit width can land between two presets: it divides the pane's `clientWidth` (less a 32px margin, so the page neither butts against the edges nor trips a horizontal scrollbar) by the base width of the page currently under the midline, then clamps into the preset range. It is a mode rather than a one-shot, so a window or pane resize re-fits (debounced by 120ms) until any manual zoom turns it off; the button carries the state as `aria-pressed`. Its icon is Folio's `fit-width` glyph, inlined as a `currentColor`-stroked SVG (no icon dependency, and it follows the toolbar's foreground in every theme) and centred with flexbox, since an inline SVG would otherwise sit on the text baseline. Stepping finds the neighbouring preset by value, so plus/minus from a fitted 137 percent goes to 150/125 percent rather than back to wherever the zoom last was.

Every scale change preserves the reading position. `captureZoomAnchor()` records the point under the middle of the viewport as fractions of its page's box (clamped to the page, since the fixed gaps between pages must not be scaled), and `restoreZoomAnchor()` scrolls that point back under the middle once the placeholders have been resized. Without it the scroll offset keeps its pixel value while the pages above it change size, which slides the view onto a different page, further the deeper into the document the reader is.

The same toolbar carries a page indicator (`3 / 12`). The current page is whichever page sits under the vertical middle of the viewport, recomputed by `pageAtViewportCenter()` on scroll (throttled to one scan per animation frame, and the scan bails out at the first page that starts below the midline, since wrappers are in document order) and again when the zoom debounce settles, because a zoom step changes page heights under a fixed scroll position without firing a scroll event. A jump's own scroll skips the recompute once (`pageJumpScrollPending`), so a target page too short to reach the midline still reads as current instead of being overwritten by its neighbour. The indicator, like the zoom percentage, is a real button, so both are keyboard-reachable; activating it swaps it for a number input: Enter jumps to that page (clamped to range) via `scrollIntoView`, Escape or blur cancels, and keydown propagation is stopped so the viewer's own shortcuts don't fire while typing.

### PDF theming, tools, comments, and scrollbars

PDF page recolouring is applied to the rendered canvas bitmap at render time, not a CSS filter or a pdf.js rendering mode. After `page.render()` finishes, `pdf.ts` recolours the pixels in place based on the page's target appearance. For dark mode it sets `globalCompositeOperation = 'difference'` and fills the canvas with white, which is an exact colour inversion (no hue rotation) of the actual pixels. For the green theme it takes that white-on-black inversion one step further, multiplying it by a phosphor green (`#00ff00`, matching the green palette's `--mc-fg` and GNOME Terminal's "Green on black" profile) so the page reads as green-on-black phosphor; `multiply` leaves the black background black. An earlier version used a CSS filter (`filter: invert(1) hue-rotate(180deg)` on the canvas element, the same trick used by [Folio](https://github.com/owenpkent/folio)), but a CSS filter forces the browser to re-rasterise the layer at CSS resolution, which blurs pages on HiDPI displays; baking the recolour into the bitmap keeps the oversampled render crisp.

Which recolour a page gets is decided by `pageAppearance()` in `pdf.ts`, returning one of `normal` (true colours), `inverted` (dark), or `green` (the phosphor variant). It follows `markcopy.theme` like the Markdown preview: `green` yields the phosphor look, `dark` (or auto mode on a dark VS Code theme) yields the inversion, everything else stays `normal`. The PDF viewer carries the same **Theme** submenu as the Markdown preview (**Auto** / **Light** / **Dark** / **Green on black**), nested under its **Preferences** submenu; picking one posts `updateSetting` to persist the shared `markcopy.theme` (see [Message protocol](#message-protocol)) and re-tints the pages. Separately, a session-only **Dark Pages** / **Light Pages** quick toggle (`pageMode` in `pdf.ts`, one of `auto` / `normal` / `inverted`) does a one-off inversion that overrides the appearance without changing the saved theme. Either way, toggling clears every rendered page and re-rasterises the visible ones, since the recolour is baked into the bitmap rather than a live filter. **Copy Page as PNG** still copies the page in true colours for every appearance: for `inverted` it fast-inverts a throwaway copy of the canvas back, and for `green` (where the phosphor multiply is not exactly reversible) it re-rasterises the page clean. A `forced-color-adjust: none` rule on the page root keeps Windows High Contrast from recoloring page content.

Because pages now have a real text layer, `pdf.ts` no longer treats every drag as a pan. The **Preferences** submenu toggles between a **Hand Tool (Drag to Scroll)** and a **Pointer Tool (Select Text)** (`mode` in `pdf.ts`, `'hand'` or `'pointer'`, starting in hand mode). Hand mode drags anywhere on the page area to pan (pointer events, with pointer capture so a drag that leaves the webview still delivers `move`/`up`, and the cursor switching between `grab` and `grabbing` via the `mc-grabbing` body class); pointer mode leaves drags to the browser's native text selection instead.

Comments are pin notes: right-click a page and choose **Add Comment Here** to drop a pin at the click position (stored as a fraction of the page's width/height, `xPct`/`yPct`, so pins stay put across zoom) and open an editable note popover; clicking an existing pin reopens that popover to edit or delete it. Comments persist to a sidecar JSON file next to the PDF, `<filename>.pdf.mccomments.json`, written and deleted by `pdfEditor.ts`'s `writeComments` (an empty array deletes the file) so the PDF itself is never modified; the webview sends the full current array via a `saveComments` message on every add, edit, or delete, and receives the saved array back in the `load` message's `comments` field when the PDF is reopened.

The PDF view also gets always-visible, styled scrollbars, scoped to the PDF page's root element (`html.mc-pdf-root`) so the Markdown preview's scrollbars are unaffected.

## Spreadsheet preview

An `.xlsx` is binary, so it never becomes a `vscode.TextDocument`. Every load-bearing part of the preview pipeline is TextDocument-shaped (`update()` renders from `doc.getText()`, live updates hang off `onDidChangeTextDocument`, `previewKind()` keys off `languageId`, the CSV writeback applies a `WorkspaceEdit` over byte offsets), so none of it reaches. `contributes.customEditors` plus `workspace.fs.readFile` is the route, the same one the PDF viewer takes.

Where it differs from the PDF viewer, deliberately: **it ships no webview code of its own.** `XlsxEditorProvider` serves the same `htmlShell()` as the Markdown/CSV preview, loads the same `media/webview.js`, and posts the same `render` message. The host renders a sheet into the CSV grid's exact markup, so the sheet inherits the context menu, every **Copy as** flavor, column resizing, the four palettes, and Save as PDF without a line of new webview code. `src/webview/pdf.ts` is a thousand lines largely because that reuse was not attempted there; the only new webview code here is a click handler that posts `selectSheet`.

Three properties fall out of the markup rather than out of conditions in the webview, which is what keeps them from being lost to a refactor:

- **Read-only.** `src/csv.ts` marks its grid `data-mc-editable`, and `csvEdit.ts` wires only tables carrying it. A sheet omits it. A cell edit has nowhere to go: the document is a binary workbook, not a text file with addressable lines.
- **Out of scroll sync.** A sheet emits no `data-source-line`, so the anchor list is empty and there is nothing to report. There is no visible text editor to reveal into either way.
- **Chrome stays out of copies.** The sheet tab strip and the row-number gutter carry `data-mc-ignore`. So does the column-letter header row, which labels the grid rather than being part of it, and `tableToDelimited` drops a row that contributes no data cells so it does not become a blank line.

Parsing runs on the host, in `src/xlsx/`, free of the `vscode` module. That is where this feature's bugs live (serial-to-date arithmetic, format-code resolution, merge geometry, the `t="s"` versus `t="str"` distinction), and keeping it pure means vitest reaches all of it with no webview and no bundle. Two format details worth knowing, because previews get them wrong: a cell's `s` indexes `cellXfs`, not `cellStyleXfs`, and date-ness is decided by the format **code**, never by the format id (the common "14-22 means date" heuristic misses builtins 45 to 47 and the East Asian blocks, and anything from 164 up means whatever that file says).

The container is hostile input before a tag is parsed, so `zip.ts` caps file size, entry count, per-entry size, and total inflated size, and refuses external relationships (`externalLinks`, remote images, DDE/OLE links), which are SSRF and, on Windows, credential-leak vectors. Entity expansion needs no defence: saxes resolves only the five predefined XML entities and never expands DTD-declared ones, so a billion-laughs payload is inert. `tests/xlsx/reader.test.ts` pins that, so swapping the parser for one that does expand them fails the suite rather than the extension host.

## PowerPoint preview

A `.pptx` is binary for the same reason an `.xlsx` is, so it takes the identical route: `contributes.customEditors` plus `workspace.fs.readFile`, handled by `PptxEditorProvider` (`src/pptxEditor.ts`), the sibling of `XlsxEditorProvider` and built the same way, no webview code of its own, the same `htmlShell()` and `media/webview.js`, the same `render` message (`kind: 'pptx'`). Parsing runs on the host, in `src/pptx/read/`, free of the `vscode` module, so vitest reaches slide order, placeholder inheritance, EMU-to-percent conversion, bullet nesting, table merges, the media budget, and scheme colour resolution without a webview or a running editor. `PptxEditorProvider` also watches the file for external changes, since PowerPoint saves by writing a temp file and renaming it over the original, which arrives as a delete followed by a create rather than a plain change event.

**One scrollable column, not one slide behind a tab strip.** This is the one deliberate divergence from the spreadsheet preview just above, and the opposite choice for the opposite reason: a workbook is a working surface you point at, so it shows one sheet and a tab strip; a deck is a document meant to be read end to end, and the whole point of this extension is getting content _out_, so rendering the whole thing as one scrollable column is what lets Copy Whole Document, Save as PDF, Save as Word, and Save as PowerPoint take the whole deck in one go rather than whichever slide happened to be on screen. `markcopy.pptx.maxSlides` caps how many slides render before the preview stops and says how many it hid.

**Two coordinate systems, no JavaScript.** DrawingML positions shapes absolutely, in EMU (914400 per inch), against a slide of whatever size the presentation declares, and the preview has to scale that to whatever width the panel happens to be without a resize handler: this same HTML is also what `html-to-image` rasterizes for Copy as PNG and what headless Chrome prints for Save as PDF, and a layout that needs script to stay correct is a layout that exports wrong. So `render.ts` emits positions and sizes as **percentages** of the slide box, exact under any scale, and font sizes in **`cqw`** against a `container-type: inline-size` slide, so text scales with the box: one multiplication per value at render time, nothing to re-run on resize.

**DOM order is reading order, not z-order.** Shapes are emitted title first, then body placeholders, then everything else top to bottom and left to right, regardless of where the file positioned them; `layout.ts` resolves the placeholder-inheritance chain (slide -> layout -> master) once per layout and caches it, since slides overwhelmingly share a handful of layouts, and through them a master and a theme. Absolute positioning is what the eye follows on screen; DOM order is what a copy, a screen reader, and the Word/PowerPoint exports follow instead, and those must not inherit whatever z-order the file happened to be saved in. For the same reason the elements are semantic and only incidentally positioned: a title placeholder is a heading, body text is a paragraph or list, an `a:tbl` is a real `<table>`, and a picture is an `<img>` carrying its shape description as alt text, so a Word paste or Save as Word is left with a readable document once the positioning is dropped.

Each slide carries `data-source-line="<index>"`, which is what the shared webview keys the per-block copy menu off. There is no `TextDocument` behind a deck, so the panel reports `supportsSync: false` and that attribute never feeds scroll sync, only the menu.

**What it will not draw.** Charts, SmartArt, OLE objects, embedded media, transitions, and animations. Each becomes a labelled placeholder box naming what it is, never a blank: a deck is mostly text and pictures, and those are drawn properly, where pretending to render a chart would be worse than admitting there is one.

The container is hostile input before a tag is parsed here too, through the identical guarded unpacker a workbook goes through (`openZip()` in `src/ooxml/zip.ts`; see [OOXML container](#ooxml-container) above), so the same size, entry-count, and external-relationship refusals apply to a crafted `.pptx` as to a crafted `.xlsx`.

## Word preview

A `.docx` takes the same route as a deck: `contributes.customEditors` plus `workspace.fs.readFile`, handled by `DocxEditorProvider` (`src/docxEditor.ts`) on the shared `OoxmlEditorProvider` scaffold, with no webview code of its own. The `render` message carries `kind: 'docx'`; the webview treats it as any other HTML document, which is why the context menu, every Copy as flavor, the exports, and Search Google all work without a line of new code. There is no `TextDocument`, so `supportsSync` is false and the blocks carry no `data-source-line` (a value there would make the per-block Markdown copy slice an empty `source`).

Data flow: `renderDocxHtml(bytes)` opens the package through `openZip()` (the same size, entry-count and per-part limits as a workbook), finds the main part through `_rels/.rels` (falling back to `word/document.xml`), parses `styles.xml` and `numbering.xml` (a missing or broken one costs fidelity, never the document), reads `footnotes.xml` and `endnotes.xml`, then walks `w:body` into HTML strings in document order. A malformed or missing body throws `DocxError` with a message written to be shown, and the editor turns that into a notice in the panel; the DOMPurify pass and CSP in the webview are unchanged.

Decisions worth knowing before changing it:

- **Headings.** `Styles.heading()` resolves a paragraph's own `w:outlineLvl` first, then walks its style chain nearest first, taking the first style that states an outline level or is named Title or Heading 1 to 9 (by id or by name, so a localized id still works). Title becomes `h1` with class `mc-docx-title` and Heading 1 is also `h1`; levels past 6 clamp to `h6`; outline level 9 means body text. A heading is never also a list item, even when its style carries multilevel numbering.
- **Lists.** A list is a run of paragraphs that name a `numId` (directly or through the style). One list is open at a time. A deeper item continues the open list as a sublist even under a different `numId`, and a bullet continues an open bullet list, because Word writers, this extension's own export included, mint a fresh `numId` per sublist; two ordered lists with different ids stay apart, since that is how a restart is written. A list interrupted by other content and then resumed carries its count on through `ReadCtx.counters` as the `start` attribute. Blank paragraphs never split a list.
- **Code.** A paragraph whose every visible run is monospace (by font name, from the run, its character style, or its paragraph style) becomes part of a `<pre><code>` block, but only at the top level; inside a table cell or a note it stays a paragraph with inline `<code>`.
- **Tables.** `vMerge` is folded into `rowspan` on the starting cell by column position, never across the head/body boundary; a continuation cell with nothing to continue stays an ordinary cell. Header rows are only the leading `w:tblHeader` rows. A row that starts with `w:gridBefore` skipped columns gets empty leading cells (`leadingGaps`), so its cells keep their columns in the HTML and in per-table CSV and TSV copy. Nesting is capped at 8.
- **Links and ids.** Only `http`, `https` and `mailto` survive as `href`; the target comes from the `External` relationships `readExternalRels` returns, which `readRels` still refuses everywhere else. Bookmark names become element ids with a `mc-bm-` prefix and a restricted character set, so a hostile name cannot clobber the shell's own ids or break out of the attribute.
- **Equations.** `omml.ts` converts an `m:oMath` subtree to LaTeX and nothing else: no DOM, no `vscode`, no throwing. `inline.ts` wraps the result in the markup `render.ts` emits for Markdown math (`class="mc-math"` with `data-display`), so the webview's existing `renderKatex()` pass renders it and the existing math context menu (copy as LaTeX or PNG, and Turndown's `$...$` restoration) applies with no webview change. `m:oMathPara`, or an `m:oMath` that is the only content of its paragraph, is display math; a display equation alone in a paragraph is a `<div>` and the paragraph gets no `<p>` (a `<div>` inside a `<p>` is closed early by the HTML parser), otherwise it is a `<span>`. Namespace prefixes are stripped by the shared parser, so `m:r` and `w:r` are both `r`; the converter only walks inside `m:oMath`, where that is unambiguous. Writers differ: pandoc uses `m:sty`/`m:scr` run properties and a literal `&` for equation-array alignment, LibreOffice marks operators as normal text and writes function names as plain runs, so the run handler reads an upright run that is exactly a function name as that function, and normal-text runs with no letter or digit as math symbols. Unknown elements convert their children; recursion depth, visited-node count and output length are capped (an over-long result is dropped, not cut mid-command). Run text is charged against `MAX_LENGTH` (100,000 characters) as it is read, so an oversized equation is abandoned early and renders as nothing. `m:sty` bold also applies to digits and Greek: Latin letters and digits are upright `\mathbf`, while Greek gets `\boldsymbol` because `\mathbf` leaves lowercase Greek italic. `ReadOptions.math` (fed from `markcopy.math` by `DocxEditorProvider`, which also redraws when it changes) turns equations into `<code>` LaTeX.
- **Images.** Delivered as `data:` URIs through `imageDataUri`, the way the deck does it, with a 16 MiB budget (`maxMediaBytes`). The budget is the document-wide output budget in `ReadCtx.output`, charged through `spendOutput` for every emitted image reference, not once per unique part, so a picture repeated many times cannot multiply the preview. A linked (never fetched), unsupported or over-budget picture is a labelled `mc-docx-placeholder`; a refused charge also marks the result truncated and appends the note "Some repeated images or charts are not shown, to keep the preview a reasonable size." For `mc:AlternateContent` only `Choice` is read (`Fallback` only when there is no `Choice`), since the other branch is a second copy of the same content.
- **Run formatting from styles.** A paragraph style's run properties (bold, italic, hidden and so on) apply to every run in the paragraph. They are merged as paragraph style, then character style, then direct formatting, so the nearer source wins. Bold inherited from a heading or header-cell style is not repeated inside the heading or cell.
- **Revisions and fields.** `w:ins` and `w:moveTo` are read, `w:del` and `w:moveFrom` are not. Field instructions are never shown; a `HYPERLINK` field becomes a link, anything else shows its cached result.
- **Bounds.** Empty paragraphs are dropped rather than emitted as spacing. A paragraph budget (50,000, counting those in tables) stops the walk and says so.

- **Headers and footers.** `sectionProps()` lists the section properties in order. The header is the first section's default (else first-page) `w:headerReference`; the footer is the last section that names one, since a section without its own inherits. The part is resolved through the document rels and rendered with the normal block reader under the header part's own rels, so its images and links resolve there. `PAGE`, `NUMPAGES` and `SECTIONPAGES` field results are dropped everywhere (`PAGEREF` is kept). Both elements carry `data-mc-ignore`, and one that is empty after that is omitted.
- **Block content from inside a paragraph.** A text box or chart cannot live inside a `<p>`, so the inline reader pushes finished markup onto `ctx.afterPara` and `renderBlocks` drains it right after that paragraph (closing any open list, quote, or code block). Text boxes are `<aside class="mc-docx-textbox">`; `collectBoxes` picks one `mc:AlternateContent` branch so text is never duplicated, and nesting is capped at 4. Pictures inside a text box are read once, inside the box, for DrawingML and VML: `findAll` takes a `stop` predicate so the paragraph's own picture search does not descend into a box.
- **Comments.** `comments.xml` is read into `ctx.comments`. `commentRangeStart` and `End` become `<mark class="mc-docx-comment" data-mc-comment>` open and close atoms; a range that crosses paragraphs is re-opened in each (`ctx.openComments`), and overlapping ranges close and reopen so each mark keeps its own text. The marker is `<sup data-mc-ignore>`; the section is `data-mc-ignore`. Threads come from `commentsExtended.xml`: a comment's `w14:paraId` is its last paragraph's, and `w15:paraIdParent` nests a reply (cycles are ignored). The webview's `stripViewerChrome` removes `[data-mc-ignore]` and unwraps `mark[data-mc-comment]`, and `selectionMarkdown`, the plain-text read in `copyRichText`, and `copyRichFromSelection` apply the same rule, so none of it reaches the clipboard or an export. For a selection containing chrome, the `text/plain` flavor is rebuilt by `blockText` (paragraph breaks, a tab between table cells); a selection without chrome keeps the browser's own selection text.
- **Charts.** A `c:chart` reference resolves to `word/charts/chartN.xml`; the reader draws only what the chart cached (`strCache`, `numCache`, multi-level categories use the innermost level, scatter uses `xVal` and `yVal`), as a `<figure class="mc-docx-chart">` holding an ordinary `<table>`, which is why per-table CSV, TSV and Markdown work on it. Each chart part is parsed once per document (`ctx.chartCache`), and each reference charges its figure's HTML length against the same output budget as images; past it the chart is a "Chart (not shown, size limit reached)" placeholder. Only percent and fixed-decimal format codes are applied. A chartex (`cx:`) chart, a missing part, or a part with no cached values is a labelled placeholder. Caps: 2,000 rows and 64 series.

Not read: SmartArt, embedded objects, page numbers, comment ranges that start or end between blocks (outside any paragraph), section properties other than header and footer references, and anything about page layout.

## STL preview

Ported from [MeshView](https://github.com/owenpkent/meshview), which this supersedes. It takes the same `contributes.customEditors` + `workspace.fs.readFile` route as the PDF and spreadsheet previews, and like the PDF viewer it ships its own webview bundle. Unlike the spreadsheet preview it cannot reuse `htmlShell()` and `media/webview.js` at all: there is no HTML document to render into, only a `<canvas>` a WebGL renderer draws into, and no copy actions to hang off the shared context menu. A triangle soup has no text, tables, or images to put on a clipboard. So `src/stlEditor.ts` serves a small self-contained page and `src/webview/stl.ts` drives Three.js inside it.

Three.js is its own esbuild entry point (`media/stl.js`, ~547 KB minified) rather than a lazy chunk of `media/webview.js`, so it is fetched only when an `.stl` is opened and the Markdown, CSV, and PDF previews pay nothing for it.

Two decisions in `src/webview/stlInfo.ts` are the load-bearing ones, and both are about not trusting a length:

- **The file is hostile input.** A binary STL is an 80-byte header, a uint32 triangle count, then 50 bytes per triangle, and `STLLoader` sizes its `Float32Array`s from that count without checking the file is big enough to hold them. A crafted 84-byte file declaring `0xFFFFFFFF` triangles asks for tens of gigabytes. `checkStl()` runs first and refuses any file whose declared count needs more bytes than the file has, or exceeds `MAX_TRIANGLES` (~5.4 million), or is simply larger than `MAX_STL_BYTES` (256 MiB). That last one applies to ASCII too: an ASCII parse cannot amplify, but a multi-gigabyte one still freezes the webview. The checks run host-side (the size off `stat`, before a byte is read) as well as in the webview, so a hostile file is never read, encoded, and shipped just to be refused on arrival.
- **The message payload is hostile input too.** The host sends base64 rather than a `Uint8Array` because `webview.postMessage` JSON-encodes, and JSON turns a typed array into a numeric-keyed object roughly 13x the size (a 5 MB model becomes ~67 MB of JSON). `toBytes()` decodes that, and its fallback branches never allocate from an unvalidated `length`: a bare `{length: n}` is refused rather than fabricated into `n` zero bytes, which would otherwise sniff as a valid empty STL and hide a transport bug as a file problem.

Both are pure and unit-tested in `tests/stlInfo.test.ts`, which is the point of keeping them out of the Three.js path.

## Video preview

`.mov`, `.mp4`, and `.m4v` take the same `contributes.customEditors` route as the PDF, spreadsheet, and STL previews, and the same self-contained-page shape as the STL one, but they invert the data flow every other preview uses.

**The host never reads the file.** `src/videoEditor.ts` calls `webview.asWebviewUri(document.uri)` and posts the resulting URI; the `<video>` element requests it and VS Code's resource protocol serves ranges as playback and seeking need them. Reading a video the way `pdfEditor.ts` reads a PDF would mean the whole file in the extension host, again as a base64 string at 1.33x, again as JSON through `postMessage`, and again decoded in the webview. For the 4 MB PDF that is a rounding error; for a 4 GB screen recording it takes the window down, and there is no size at which it buys anything, because the element can stream. This is also why there is no `MAX_VIDEO_BYTES` guard equivalent to `MAX_STL_BYTES`: nothing here allocates in proportion to the file.

The consequence is that the file's own directory has to join `media/` in `localResourceRoots`. Workspace folders are roots by default, but a video is more often opened from outside the workspace than any other type this extension handles, and without its directory the element is handed a URI the webview refuses to serve.

**Frame grabs and canvas tainting.** The video is served from a `vscode-resource` origin, which is not the webview document's own, so `drawImage` from it taints the canvas and `toBlob` throws a `SecurityError`. VS Code serves webview resources with `Access-Control-Allow-Origin: *` (the same header that lets `src/webview/pdf.ts` `fetch()` its worker), so the element requests the file with `crossOrigin = 'anonymous'` and the canvas stays clean. A host without that header would fail the load outright and indistinguishably from an unplayable codec, so the `error` handler retries once without the attribute: if that plays, the only casualty is the frame actions, and `frameCopyBlocked` makes them say so rather than fail silently.

**Codecs, and the proxy that gets around them.** QuickTime is a container, not a codec. VS Code's Chromium decodes H.264 video, which is what screen recordings and phone clips are, but it ships no AAC decoder (VS Code's own Media Preview docs say mp4 "does not support aac audio tracks"; see microsoft/vscode#167685), so those files play silently with no error event. It does not decode ProRes, DNxHD, or (on most builds) HEVC either, which is what a `.mov` out of a professional camera or editor usually is. Audio is no better: in the installed VS Code, AAC, Opus in MP4, AC-3 and ALAC all play silently (picture fine, zero audio bytes, no error), while MP3 (in .mp4 and .mov), FLAC in MP4, Vorbis in MP4 and PCM in .mov decode. `canPlayType` answers "probably" for every one of them, so it cannot be used to decide. This was measured on 2026-10-11 by playing each variant for two seconds in a webview and reading Chromium's `webkitAudioDecodedByteCount`. VP9, AV1 and HEVC video in MP4 decode (HEVC depends on the OS decoder). Containers are the other half, measured the same day with a probe extension: the player opens only the MP4 family, and everything else fails at once with `MEDIA_ERR_SRC_NOT_SUPPORTED` (code 4, `DEMUXER_ERROR_COULD_NOT_OPEN`), including content that plays inside an MP4.

| Container                      | Opens in VS Code's player | Video tested                                     |
| ------------------------------ | ------------------------- | ------------------------------------------------ |
| `.mp4`, `.mov`, `.m4v`, `.3gp` | Yes                       | H.264, VP9, AV1 (HEVC depends on the OS decoder) |
| `.mkv`                         | No                        | H.264 + MP3                                      |
| `.webm`                        | No                        | VP8 + Vorbis, VP9 + Opus                         |
| `.avi`                         | No                        | not recorded                                     |
| `.flv`, `.ts`, `.mpg`          | No                        | MPEG-2 for `.mpg`                                |
| `.wmv`                         | No                        | WMV2                                             |

The `.ts`, `.mts`, and `.m2ts` extensions are deliberately not registered, because `.ts` is TypeScript. The element cannot be taught the missing codecs, but the file can be re-encoded into something it already understands, and `src/videoProxy.ts` does that whenever an ffmpeg is on the machine.

The viewer drives none of the decision. It reports that the element gave up (`proxyRequest`), because every input (is ffmpeg installed, what codec is this really, has the reader set `markcopy.video.transcode` to `off`) lives on the host side of the `postMessage` boundary. `ProxySession` in `src/videoEditor.ts` owns one panel's answer: it finds ffmpeg (`findFfmpeg`, the same configured-path-wins, probe-everything-else contract as `findBrowser` in `src/pdfExport.ts`), probes the source with the `ffprobe` sitting beside that exact ffmpeg, and either encodes straight away, offers a button, or reports a dead end. Progress arrives on ffmpeg's `-progress pipe:1` stream, is throttled to four updates a second, and is drawn in place rather than by rebuilding the overlay, so the **Cancel** button keeps its focus ring for the length of the encode.

**The remux path.** A container-only failure does not need an encode. `canRemux` in `src/videoProxy.ts` is true when the source's extension is outside the MP4 family (`outsideMp4Family`), the probed codec is in `REMUXABLE_VIDEO` (`h264`, `vp9`, `av1`, the codecs measured to decode every time inside an MP4), and the source has no alpha (a pixel format with an alpha plane, or for WebM the `alpha_mode` stream tag, since transparent VP8/VP9 reports plain `yuv420p`); the picture path then runs `-c:v copy`, in seconds, with the audio still on the MP3 args. HEVC is excluded on purpose: when an HEVC file fails it is usually the codec, and copying it would fail again on a machine without the OS decoder. VP8 is excluded because it was not measured in MP4. Everything else (WMV, MPEG-2, VP8, ProRes, alpha) keeps the libx264 re-encode. A transparent WebM also needs `-c:v libvpx-vp9` (or `libvpx` for VP8) before `-i`, because ffmpeg's native VP8/VP9 decoders drop the alpha block. The extension test matters: an H.264 `.mov` or `.mp4` that the player refused was already in an MP4, so whatever broke it would survive a copy, and it takes the re-encode instead. The host's `ask` message carries `remux: boolean` and the status note is `ffmpeg copy · repackaged as MP4`. `proxyOffer` in `videoInfo.ts` combines the flag with the file's extension (`outsideMp4Family`) to say that VS Code's player cannot open `.mkv` files rather than that it cannot play H.264, and `describeMediaError` and `proxyUnavailable` name the container too.

**The sound copy.** A silent file never raises an `error`, so the webview cannot ask for help; it reports `playable` once the original fires `loadedmetadata` (not `loadeddata`, which under `preload="metadata"` can wait for the reader to press play), and `ProxySession.offerSound` decides. It probes, and only if the audio codec is not in `PLAYABLE_AUDIO` does it act: under `auto` it builds, under `ask` it posts `soundAsk`, under `off` or with no ffmpeg it says nothing (without ffprobe the codec is unknown, and a possibly wrong notice is worse than none). The build is `transcodeArgs` with `copyVideo`: the picture is stream-copied when its codec is in `COPYABLE_VIDEO`, so it finishes in seconds, and only the audio is encoded. Every message of that build carries `scope: 'sound'`, which the webview routes to a non-blocking notice bar rather than the overlay, because the original is still playing underneath. When the copy lands, `load` captures `currentTime` and the paused state before swapping `src` and restores them on `loadedmetadata`. A cancelled sound build returns to `soundAsk`.

Two decisions inside the encode are worth keeping:

- **Audio is always MP3.** Every proxy MarkCopy builds is encoded `libmp3lame` at 192 kbit/s, stereo, 48 kHz, since AAC and Opus proxies would be as silent as the file they replace (see the measurements above). `-ac 2` because MP3 carries at most two channels and a preview needs no surround; `-ar 48000` pins a rate MP3 supports regardless of the source, such as a 96 kHz master.
- **A `localResourceRoots` entry cannot be added later.** The list is fixed when the element asks for a URI, so `proxyDir()` (one predictable directory under `tmpdir()`, not a per-panel `mkdtemp`) is registered at panel-open time, before any proxy exists. Individual proxies are kept apart by a random component in the file name instead.
- **A clip with an alpha channel goes over a checkerboard, not black.** H.264 has no alpha, so something has to go behind the picture. A lower third that is 99% transparent flattened onto black produces a frame that looks exactly like a clip rendering nothing; the checkerboard says "transparent" in the language every compositing tool already uses. It is drawn once and held (`color …:d=1:r=1` → `geq` → `loop` → `fps`), because `geq` is a per-pixel expression and evaluating two million pixels per frame costs more than the encode it decorates. WebM with a real alpha channel was tried first and abandoned: neither VP8 nor VP9 preserved it through the ffmpeg build on hand, and a feature that depends on how a user's particular ffmpeg was compiled is worse than one that only needs `libx264`.

The proxy is scratch, not an export: it is deleted on `panel.onDidDispose`, nothing offers to keep it, and the status line calls it an `ffmpeg preview copy` for as long as it is on screen, including the checkerboard, which a reader grabbing a frame needs to know is baked in. When there is no ffmpeg, or the reader turned it off, the old behaviour stands: `describeMediaError()` in `src/webview/videoInfo.ts` names the likely cause per `MediaError` code and the page offers **Open in Default App**, which posts back to the host for `vscode.env.openExternal`. A viewer that cannot play a file is still allowed to be useful about why.

The provider registers with `retainContextWhenHidden`, unlike its read-once siblings, because tearing the webview down on a tab switch would restart playback from zero on the way back.

## Video review

Review mode brings the timecoded-notes loop of [Marker](https://github.com/owenpkent/Marker) into the video preview. It is a mode of the same viewer, not a second one: a video with no sidecar and `markcopy.video.review` off looks and behaves as before. The plan and its reasoning are in [VIDEO-REVIEW-DESIGN](VIDEO-REVIEW-DESIGN.md); this section describes the code. Notes can be read, written, completed, deleted, restored, filtered, sorted and pinned here, and a note added in Marker (or any tool that writes the kit's schema) appears when the file changes.

**When it turns on.** `ReviewSession.onReady()` runs after the webview's `ready`. Review mode starts if `<stem>.review.yaml` exists beside the video (`clip.review.yaml` for `clip.mp4`; only the last extension goes, as in the kit's `review_path`, so `clip.mp4` and `clip.mov` share one sidecar) or `markcopy.video.review` is true. Otherwise the right-click menu's plain **Open Video Notes** item (**Close Video Notes** once it is on) posts `reviewEnable`, and the same entry writes `video.review` through the shared `updateSetting` path, which `isViewerSetting` admits as a boolean like `video.loop` and `video.autoplay`. Nothing runs, and no watcher exists, until review mode is on.

**Messages.** Host to webview: `review` (`fps`, `fpsSource`, `sidecar` name or null, `notes`, `readOnly` reason or null), sent after every load, probe result and reload, where the first one puts the webview into review mode; and `reviewError` (a message for the toast); `review` also carries `restorable` (the id Restore would bring back) and `added` (the id this panel just added, so the webview selects it). Webview to host: `reviewEnable` and `reviewCopy`, neither carrying data, and the edits `reviewAdd` (`at`, optional `out`, `text`, optional `point`), `reviewDelete` (`id`) and `reviewRestore`. The edits carry data from the page, so each goes through an exported validator before anything is written: `reviewAddError` and `isReviewAdd` (finite `at` of 0 or more, `out` after `at`, text a string of at most `MAX_NOTE_TEXT` = 10,000 characters, times within the duration plus one frame when the duration is known, and a `point`, when present, of two finite numbers each 0 to 1, else "The pin must be two numbers from 0 to 1"), `isReviewDelete` (the id must exist in the file just read) and `isReviewRestore`. All refuse extra fields. The host allocates ids; the page never does. The types live in `src/review/protocol.ts`, imported by both bundles. Each post carries a generation number, so a slow read that began before a newer one (the watcher often fires twice for one save) cannot post stale notes last.

**The webview.** `src/webview/videoReview.ts` replaces the native controls with a transport (play, frame back and forward, speed 0.5x, 1x or 2x, and a timecode readout with the frame rate and where it came from), a scrubber carrying one marker per note, and a notes panel of cards. Markers closer than a target pitch cluster (`layoutDots`, ported from Marker's `timeline.js`) and a range note draws a bar. Pressing a marker or a card seeks to it and selects it. The panel sits beside the video and moves below it when the editor is narrower than 720 px (the panel's 320 px plus a 400 px minimum for the video). Frame steps are `1/fps` at the real rate, and a seek lands half a frame into the target frame (`seekMsForFrame`). Timecode is non-drop-frame: the frame count is taken at the real rate and labelled at the nominal integer rate, with exact halves rounded to even as Python's `round` does, so labels match the kit and Marker. Left and Right step a frame, **J K L** slow, pause and speed up, and `,` and `.` step at the real rate; **space**, **m** and **f** are unchanged. `onKeydown` ignores keys while a text field has the focus.

**The composer and card actions.** The panel foot holds **[ In**, **Out ]**, a chip for the pending range with **Clear**, play/pause, a **Note text** field and **Send**. I and O set In and Out from the playhead (ignored while typing or when the panel is read-only), Enter sends and Escape leaves the field. Focusing the field pauses; sending resumes if the video was playing and moves focus off the field, so the next key press is a transport key again. Empty text toasts "Write the note first"; Out with no In toasts "Set In first", Out at or before In "Out must be after In", and a later In at or past the pending Out drops the Out. The pending range is drawn as a band on the scrubber. The selected card shows **Delete**; **Restore nN** at the top of the panel follows a delete. With no notes file and a frame rate that is only assumed, "Frame rate unknown: notes will be saved at 30 fps" shows above the composer, and Send waits while the rate is still being read. The webview checks nothing the host does not check again.

**Sort, bands and pins.** `arrangeNotes` applies the panel's sort (`time`, `newest`: latest `created` first, ties by the higher id number), kept in the webview's saved state (`viewState`, wired to `vscode.getState/setState` by `video.ts` and merged with whatever else is saved), so it survives reopening the panel but is not a setting. There is no filter and no Done toggle (dropped after hands-on testing); a note with `done: true` from Marker renders as done, read-only, and no edit touches the flag. The scrubber markers are not filtered. Bands are drawn in a layer over the slider's own track from `bandGeometry` (range notes, brighter when selected) and `pendingBand` (the pending range, In bracket alone until Out); both are pure functions in `src/review/timeline.ts`. The stage click in `video.ts` calls `review.onPicture(e)` first: it returns false, and the click toggles play as before, outside review mode, when the panel is read-only, or while pin mode is off (the default; the **Pin** chip or **P** turns it on, and Clear, a successful send or turning it off leave it, while a failed send restores it with the draft). The panel's **×** calls the same `setReview(false)` as the menu's Close Video Notes. Otherwise it converts the press to a point on the picture, not the element (`pictureRect` and `pointInRect` account for letterboxing, so a press in the bars does nothing but is still consumed), stores a pending pin, pauses and focuses the field. `resumeAfterNote` is set only if playback was running before the first press, survives further presses, and a deliberate play or pause clears it. Send includes `point`, and Clear drops range and pin. Pinned notes (keep and reject notes too) get a numbered 44 px stud while `pinVisible` holds for the playhead; `renderPins` runs when the frame index changes, and pressing a stud selects its note and scrolls its card into view. The pending pin is a ring with a plus, named "Pending pin, press the picture to move it".

**Pin on the host.** `reviewAddError` rejects a `point` that is not two finite numbers from 0 to 1. `cleanPoint` rounds each to 4 decimals as the kit's `_clean_point` does with Python's `round`: `toFixed(4)` agrees except on an exact binary tie, where Python takes the even digit (a press 25 px into an 800 px picture is 0.03125, written as 0.0312, where `toFixed` gives 0.0313), so it checks the exact decimal expansion for a tie. `noteYaml` then writes the `point: [x, y]` line as the kit does. The markdown line is "Pin: 42% from left, 30% from top".

**Frame rate.** A `<video>` cannot report one, so the host resolves it (`resolveFps`): the sidecar's `fps`, else ffprobe's `avg_frame_rate`, else 30, shown as "30 fps (assumed)". `r_frame_rate` stays for the transcode; the two differ on variable-rate phone footage. `VideoEditor.averageFrameRate()` reads `avgFrameRate` from the same cached probe `offerSound()` uses, so there is never a second ffprobe run. Unlike `offerSound()` it probes even when `markcopy.video.transcode` is `off`, because the rate has nothing to do with transcoding, but it still needs an ffmpeg; without one the answer is the assumed 30. While the probe is in flight the source is `pending`. A sidecar with a usable `fps` never triggers the probe.

**Sidecar ownership.** The host owns the file: it derives the path from the open document (the webview never sends a path), reads it with `workspace.fs.readFile`, and validates it in `reviewFileError` against the kit's `review.schema.json` plus its cross-field rules (`out` greater than `at`, keep or reject only with `target: source`; unknown fields are rejected because the schema sets `additionalProperties` false). Only `version: 1` is valid. A sidecar that fails to parse or validate still lists whatever notes make sense, under a "Read-only: <reason>" banner, and is never written. Parsing uses the `yaml` package's `Document`, which locates each node by range, so an edit can leave everything it does not touch alone (see **Edits** below).

**The watcher.** `enable()` creates a `FileSystemWatcher` on a `RelativePattern` over the video's own directory, so a video opened from outside the workspace is covered too. Create, change and delete all re-read the sidecar and post `review`, which is how a note added in Marker appears without reopening the tab. It is disposed with the panel. Marker desktop loads the sidecar once and saves its whole in-memory copy without re-reading it, so MarkCopy cannot protect a note written while Marker has the same video open: do not edit one video in both at once (tracked upstream as owenpkent/Marker#14).

**The file write.** Copy writes the markdown on request; edits (next section) write both files. `reviewCopy` makes the host re-read the sidecar and refuse with a `reviewError` when there is none or it is invalid or another version. Otherwise it builds the markdown with `reviewMarkdown` (a port of the kit's `Review.export_markdown`, so it matches what Marker desktop writes; the webview never builds markdown, so the clipboard text and the file are the same string), writes `<stem>.review.md` beside the video, puts the text on the clipboard with `vscode.env.clipboard.writeText`, and posts a toast such as "Copied 3 notes, saved clip.review.md". The file goes to a dot-prefixed temporary name in the same folder and is renamed over the target, so a reader never sees half of it; the temporary file is deleted if either step fails. The sidecar stays the source of truth, and the markdown is derived output that is never read back. There is no dialog: the path comes from the document's own name. That is the exception to the video editor otherwise writing only through a save dialog, with the PDF preview's `.pdf.mccomments.json` as the precedent for a silent write beside the document. [SECURITY](../.github/SECURITY.md#video-preview) covers the validation.

**Edits.** `add`, `delete` and `restore` on `ReviewSession` each go through one promise queue, so two edits never interleave. An edit runs in `commit`: it re-reads the sidecar from disk, refuses when the file is read-only (parse or schema failure, another version), validates the message against the fresh content, builds the new text, writes it atomically (temporary file, then rename), then rewrites `<stem>.review.md` from the result and posts `review`. A failed markdown write reports "Saved the notes, but could not write ..." and keeps the notes. The first `reviewAdd` on a video with no sidecar creates it with `newSidecarText`, which is what the kit's `Review.new` followed by `save` writes (a 12-hex-digit id, the video name as `source`, the resolved fps, `next_note_id: 1`, an empty `asset`); it waits for any frame rate probe in flight, since the probe decides the fps and the duration the times are checked against. The watcher ignores the change event raised by the host's own write (`lastWritten`). Delete holds the removed note's text in memory (`held`), one level and per panel; restore puts it back at its old position under its old id and leaves `next_note_id` alone. A note id the panel wrote is remembered in `written`; if a reload shows one missing, the panel posts "Notes were replaced by another program", which is Marker saving its stale copy (owenpkent/Marker#14).

**Why a splice.** The kit saves with PyYAML (`safe_dump`, `sort_keys=False`, `default_flow_style=None`, `allow_unicode=True`), and Marker and cutline read the same file, so a MarkCopy edit must not make the file churn. Parsing the file and stringifying it again would re-wrap long strings and re-pick quote styles in notes the edit never meant to touch. Instead the `yaml` package finds the node's range and the edit splices the original text: `addNoteText` appends a block and bumps `next_note_id`, `setDoneText` changes one scalar, `removeNoteText` cuts a block, `restoreNoteText` puts it back. New text is formatted the way PyYAML would (`pyString` picks the scalar style and wraps at PyYAML's width, `pyFloat` writes floats with a fraction and Python's exponent form). Line endings are detected, so a CRLF file stays CRLF.

**Byte compatibility, measured.** `tests/fixtures/review/generate.py` runs the kit's own `Review` through 19 edits (add first, point, range, multi-line, unicode, long text, reserved words, number-like text, empty text, add to a full file, five pins, remove first, middle and last) and writes each before/after pair under `tests/fixtures/review/edit/`, with `cases.json` saying which edit made which pair. `tests/videoReview.test.ts` applies the same edit to each `before` file and requires the `after` file byte for byte. Like the markdown fixtures, CI only compares; regenerating needs Python and the kit. The pairs hold no exact rounding tie; `cleanPoint` is pinned separately in `tests/videoReview.test.ts` against values from Python's own `round(v, 4)`. Known exceptions, outside those pairs: the strings `y`, `n`, `.` and exponent-like strings such as `e2` are quoted where PyYAML leaves them plain; both read them back as strings. The kit's `Review.load` and `validate` accepted every MarkCopy-written file tested.

## LaTeX preview

`.tex`, `.ltx`, and `.latex` files are handled by `TexEditorProvider`, a `CustomTextEditorProvider` registered for the `markcopy.texPreview` view type, contributed at `priority: "option"` rather than the `"default"` every other binary preview (PDF, spreadsheet, presentation, STL, video) uses. Those five are `"default"` because the file has no useful text form to fall back to; a `.tex` file does, it is what its author spends most of the day editing, so opening one has to keep giving them the text editor. The preview arrives as a second tab beside that editor, though, without being asked for: `markcopy.autoPreview` covers LaTeX the same as Markdown, CSV, and TSV, so opening or focusing a `.tex` file also opens (or reveals) its preview tab automatically, see [Auto-open preview](#auto-open-preview) for how that route differs from the shared panel's. The preview is still reachable by hand too (**Reopen Editor With...**, **MarkCopy: Open Rich Preview to the Side**, or setting it as the default for the glob).

Rather than adding a fifth webview entry point, the LaTeX preview compiles the document to a PDF and hands the result to the exact same pdf.js bundle the PDF preview already uses (`media/pdf.js`, still built by the existing `esbuild.web.js` target for `src/webview/pdf.ts`, which this feature left untouched). So the LaTeX preview inherits the PDF viewer's whole feature set for free: Copy Selection, Copy Page N as PNG, the zoom toolbar, the Theme submenu, and pinned comments. The compiled PDF reaches the webview the same way the PDF preview's own bytes do, base64-encoded in a `load` message (`postMessage` cannot carry a `Uint8Array` intact), rather than through a `localResourceRoots` entry the way the video proxy's transcoded file does. That is also why `resolveCustomTextEditor` never widens `localResourceRoots` to cover the output directory: the webview never fetches a URI out of it, it only ever receives finished bytes.

Compiling lives in `src/texCompile.ts`, free of the `vscode` module. `findTex` looks for `latexmk` first, then `tectonic`, then the bare engines (`pdflatex`, `xelatex`, `lualatex`), because the first two drive their own multi-pass build (rerunning until cross-references and the bibliography settle) and are worth using whenever either is installed; a bare engine instead gets rerun once more by `compile()` itself if its log says references are still unresolved. `-shell-escape` is never passed, for any engine, under any circumstance: it lets a document's own source run arbitrary shell commands via `\write18`, and the entire point of a preview is that opening someone's repository must not run whatever it contains.

**The output directory.** Compiled output goes to `<tmpdir>/markcopy-tex/<hash>`, one fixed directory per root file (`outDirFor`, hashing the resolved, case-normalized absolute path) rather than a fresh directory per compile. That is deliberate: latexmk keeps its own `.aux` and `.fdb_latexmk` state between runs, and reusing the same directory is what makes a recompile the fast, incremental one instead of a cold rebuild every time. The directory is created strictly (`ensureTexDir`, a non-recursive `mkdir` at each of its two levels, refusing anything that already exists as a symlink or is owned by someone else), kept alive for the whole life of the panel, and deleted (`removeQuietly`) only when the panel is disposed, taking the `.log`, `.aux`, `.bbl`, and everything else the engine left beside the PDF with it. A window that never gets the chance to clean up (a crash, a forced quit) leaves its directory behind, which is what `sweepTexRoot` is for: fired once from `activate()`, it deletes any output directory older than 24 hours, long enough that a document left open overnight keeps its PDF, short enough that abandoned directories do not accumulate indefinitely.

**Root-file resolution.** A LaTeX project is often a root file that `\input`s chapters, and the document open in the editor is not always that root. `resolveRootFile` decides what to actually compile, in order: the `markcopy.tex.rootFile` setting, if set; failing that, a `% !TEX root = ...` magic comment in the document's first 20 lines; failing that, the document itself. `CompileSession.affectedBy` uses the resolved root's own directory to decide whether a saved `.tex`, `.bib`, `.sty`, `.cls`, or `.tikz` file should trigger a recompile, so saving a chapter or a bibliography file redraws the preview too, not only saving the root.

**The `texState` message.** The host reports compile status to the webview with `{ type: 'texState', state, text?, detail?, action? }`, independently of the `load` message that carries a successful compile's bytes. `state` is one of `compiling`, `failed`, `unavailable`, or `ok`; `text` is the human-readable summary (built by `src/texInfo.ts`, which formats parsed `TexError`s into something a writer can act on rather than shipping the raw log to the webview); `detail` is the engine's own log line, shown in a smaller monospace block for the cases where the summary alone is not enough; `action` labels a button (`Compile` in `ask` mode, `Recompile` on failure) and is absent for states no button can help with (compiling switched off, no engine found), on the theory that a button that cannot help is worse than no button. `src/webview/pdf.ts`'s `handleTexState` builds this overlay lazily (`ensureTexOverlay`) on the first such message, so a plain `.pdf`, whose host (`pdfEditor.ts`) never sends one, never touches this code path at all. Receiving any `texState` message also flips a `texMode` flag that gates the "Recompile LaTeX" entry in the right-click menu, so that entry is exactly as absent from a plain PDF's menu as the overlay itself.

A webview loading more than once is itself new behavior this feature required: the plain PDF preview only ever loads once, so `resetViewer()` (which cancels any in-flight page renders and clears the page list before a `load` message is applied) did not need to exist until a recompile could hand the same webview a second PDF. Without it, every recompile would append to the existing page list while the DOM was rebuilt underneath it, leaving page navigation, comment pins, and Copy Page as PNG addressing detached elements left over from the previous compile.

## Theming

`media/preview.css` defines the palette as CSS custom properties (`--mc-fg`, `--mc-bg`, `--mc-border`, code/table/link colors, and the highlight.js tokens), with GitHub-light values as the default. A single selector block overrides them with GitHub-dark values, so the rest of the stylesheet references variables and never repeats a color.

The `markcopy.theme` setting (`auto` / `light` / `dark` / `green`) is passed to the webview in the `render` message and applied as a `data-mc-theme` attribute on `body`. The STL viewer follows the same attribute, but resolves it to a single `--mc-stl-bg` custom property, since all it has to tint is the WebGL clear color behind the model. The video viewer does the same with `--mc-video-bg` for the letterbox around the picture, defaulting to a dark surround rather than the page white a light theme would otherwise put around a dark clip. The dark override fires when:

- `body[data-mc-theme='dark']` (forced dark), or
- `body.vscode-dark` / `body.vscode-high-contrast` and `data-mc-theme` is not `light`, `dark`, or `green` (auto mode following the VS Code theme).

Because auto mode keys off VS Code's own `vscode-dark` body class, the CSS palette updates live when the editor theme switches. Mermaid diagrams are pre-rendered SVGs with baked-in colors, so to re-theme them the host also re-renders on `onDidChangeActiveColorTheme`, and on `onDidChangeConfiguration` for `markcopy.theme` / `markcopy.mermaid`. The PDF editor reads the theme setting when it opens.

Copies stay light regardless of the displayed theme: see `.mc-force-light` under [Clipboard](#clipboard).

## Content Security Policy

The webview HTML declares a strict CSP with a per-load nonce:

```
default-src 'none';
img-src ${cspSource} https: data: blob:;
style-src ${cspSource} 'unsafe-inline';
font-src  ${cspSource} data:;
connect-src ${cspSource};
script-src 'nonce-${nonce}' 'strict-dynamic';
```

Only the nonce-tagged bundle can execute, and it loads as `<script type="module">`. `'strict-dynamic'` is what makes the code-split build work under CSP: the nonce'd entry module can `import()` its sibling `media/chunk-*.js` chunks (Mermaid, KaTeX, html-to-image, Turndown) even though those chunks carry no nonce of their own, because `'strict-dynamic'` propagates trust from the entry module to the scripts it loads. `blob:` and `data:` image sources are allowed so Mermaid SVGs and html-to-image output render. All local assets are referenced through `webview.asWebviewUri`. `connect-src ${cspSource}` was added for math: rasterizing an equation to PNG (`copyPng`, see [PNG copy](#png-copy)) needs `html-to-image` to `fetch` and inline KaTeX's web fonts, which requires a `connect-src` grant; Mermaid never needed one because it renders with system fonts. The directive is scoped to the webview's own origin, so it cannot reach any external host.

See [SECURITY.md](../.github/SECURITY.md) for the threat model.

## Testing

Three automated layers. Two of them match the two runtimes; the third sits between, and exists because "inside a webview" turned out to be less out of reach than it looks:

- **Unit (`tests/`, vitest + jsdom).** Covers the pure, host-independent logic: markdown-it rendering and source-line mapping (`src/render.ts`), CSV/TSV parsing, delimiter sniffing and grid rendering (`src/csv.ts`, `tests/csv.test.ts`), CSV column resizing and cell editing driven against the real grid markup (`src/webview/csvTable.ts` and `src/webview/csvEdit.ts`, with `tests/csvEditModel.test.ts` covering the field spans and the document edits they produce), CSV/TSV clipboard serialization (`src/webview/table.ts`), HTML-to-Markdown conversion (`src/webview/markdownConvert.ts`), image-src classification plus the preview-kind and auto-preview decisions (`src/preview-utils.ts`, `tests/preview-utils.test.ts`), scroll-sync interpolation (`src/webview/scrollSync.ts`, `tests/scrollSync.test.ts`), the PDF export's browser discovery, command line, export page, and print stylesheet (`src/pdfExport.ts`, `tests/pdfExport.test.ts`), STL sniffing plus the allocation guards that run before `STLLoader` (`src/webview/stlInfo.ts`, `tests/stlInfo.test.ts`), and the video preview's duration, size, timecode, frame-filename, and media-error formatting (`src/webview/videoInfo.ts`, `tests/videoInfo.test.ts`). These were extracted from `main.ts` / `extension.ts` specifically so they import without a DOM or the VS Code API. Run with `npm test`.
- **Webview E2E (`tests/e2e/`, on `tests/webview/harness.ts`).** Boots the real bundle (`src/webview/main.ts`) in jsdom against the host's own renderers, then drives it the way a reader does: right-click an element, walk the context menu, read the clipboard flavors that come out. Covers which rows the menu offers for a given target, what each copy action writes, the sheet grid and its tab strip, what a sheet hands the host to print, and scroll sync in both directions including the echo suppression that keeps preview and editor from fighting. Nothing in it reassembles the bundle's steps, which is the whole point: a transform can be correct while the menu row that calls it has been deleted, and only this layer notices. The STL viewer is not here: it is a separate bundle with no shared shell and no clipboard surface, and what it does need (WebGL) jsdom has no more than canvas. The video viewer is absent for the same kind of reason: jsdom has no media pipeline, so a `<video>` there never reaches `loadedmetadata` and never has a frame to grab. Run with `npm test`.
- **Integration (`test-integration/`, Mocha + `@vscode/test-electron`).** Runs the built extension in a downloaded VS Code instance (`.vscode-test.mjs` config, compiled via `tsconfig.integration.json` to `out/`) and asserts activation, command registration (including `markcopy.openSettings`), configuration defaults (including the `autoPreview` default), that the preview panel opens, that focusing an on-disk Markdown file auto-opens a preview for it, and which editor claims a `.md`, `.xlsx`, `.xlsm`, `.pdf`, `.stl`, `.mov`, or `.mp4`. The `.md` case asserts both halves, that a plain open stays in the text editor and that `vscode.openWith` reaches the preview, since `option` priority is only meaningful as the pair. `markcopy.openSource` is checked by counting editor groups either side of the call rather than asserting a number, so it fails only if showing the source actually split one off. A third test drives the whole round trip, **Show Preview**, **Show Source**, **Show Preview**, and asserts one editor on the file at the end: that the two commands land in the same group is the cheap half, and that they do not quietly accumulate tabs is the half that broke first, twice, in both directions and for the same preview-mode reason. The `.mp4` case is there because VS Code contributes its own preview for that extension at `"priority": "builtin"`, which `"default"` outranks; if MarkCopy's entry were downgraded, the file would quietly open in the built-in player and nothing else would notice. Custom editors are contributed entirely through `package.json`, so a selector that stops matching is invisible to every other layer and leaves a workbook opening as binary junk. Run with `npm run test:integration`; on Linux and CI it needs a display (`xvfb-run`).

The webview layer inherits jsdom's blind spots: no canvas (so `Copy as PNG` and the PDF viewer's rasterisation), no `innerText` (so the plain-text half of a rich-text copy), no layout (scroll sync runs against a synthetic one the harness installs), and no stylesheet (so nothing can tell a legible palette from an applied one). Those rows stay in the manual pass, marked in [TESTING.md](TESTING.md). All three automated layers run in CI (see [CONTRIBUTING](../.github/CONTRIBUTING.md#tests)).

## Future ideas

- **Shared `pdf-core` with Folio.** The PDF preview shares techniques with [Folio](https://github.com/owenpkent/folio) (a Tauri + React desktop PDF viewer), most visibly the dark-mode inversion technique (originally a CSS filter ported by hand, now a canvas-bitmap inversion for HiDPI crispness). If the overlap grows (text extraction, page-to-PNG, reading-mode filters, outline/nav), consider extracting a small **framework-agnostic** TypeScript core both projects import, keeping each UI separate. Deliberately not done yet: today the shared surface is thin and the runtimes differ (Tauri desktop vs. sandboxed VS Code webview), so copying the one technique beat taking on a shared dependency. Extract only once the duplication is actually felt.
- **PDF comments/annotations.** Basic pin comments already exist: right-click **Add Comment Here** drops a pin with an editable note, persisted to a sidecar JSON file (see [PDF theming, tools, comments, and scrollbars](#pdf-theming-tools-comments-and-scrollbars)). The open design question for anything beyond that is deeper persistence, and it drives everything else:
  - _Sidecar JSON_ (what's implemented today, `<filename>.pdf.mccomments.json` beside the file) keeps the PDF read-only and is git-friendly, but comments are only visible in MarkCopy.
  - _Embed into the PDF_ (real `/Annots` via a writer like `pdf-lib`) makes them portable to any viewer, but requires switching the read-only custom editor to a writable one with a save flow, plus a new dependency.
  - _In-memory only_ is fine for prototyping the interaction before committing to storage.

  Pages now have a pdf.js text layer, so word-level text selection works; region- or highlight-style annotations (as opposed to today's point pins) are still unimplemented.

# File information

Look inside an executable or a package without running it. Both pages answer "what is this file?" from the file's own headers and tables, read as bytes, and neither can start the file.

## Reading a file is a step you take

Opening one of these files, which a single click in the Explorer does, shows only the file's name, its size and a **Read this file** button. Nothing inside the file is read until you press the button or run **MarkCopy: Read This File** from the Command Palette (it is enabled while one of these pages is in front). The question is asked again for each file you open: confirming one does not confirm the next. Once a page has been read, a change to the file on disk redraws it without asking again.

The reading does not happen in the extension host, which other extensions share. It runs in a worker thread with a 256 MB heap limit and a 15 second time limit; a file that goes past either ends the worker and the page shows a notice, and VS Code carries on. This limits runaway memory and time. It is not a separate process or an operating-system sandbox, and it does not count memory allocated outside the JavaScript heap, which the readers' own caps on buffers and dictionaries bound instead.

To skip the question, turn off `markcopy.fileInfo.confirm` (see [Commands and settings](settings.md)): the file is then read as soon as it is opened, still in the worker.

## Executable info preview

MarkCopy registers as the editor for `.exe`, `.dll`, `.sys`, `.ocx`, `.scr`, `.cpl` and `.efi` files (either case), so opening one shows a page about the file instead of VS Code's "file is binary" notice (after you press **Read this file**, as above). It is for answering "what is this file?" without running it.

- **Icon.** The file's own icon, above its name: the largest image of the first icon in the file, drawn at up to 48 pixels. A file with no icon of its own (most DLLs) shows none.
- **Version.** The version resource Explorer's Details tab reads: description, product, company, file and product versions, copyright, original file name and any other strings, plus the numeric versions, build flags and language.
- **File.** Type, architecture ("Any CPU" for .NET), PE32 or PE32+, subsystem, size, SHA-256, build time (or "not recorded" for a reproducible build), minimum Windows version, .NET runtime, linker version, image base, entry point, size in memory, header checksum, and any data appended after the program, such as an installer payload.
- **Signature.** Whether an embedded Authenticode signature is present, and the signer, organization, issuer and certificate validity dates it names, plus the digest algorithm, the certificate's public key (kind and size) and its SHA-1 thumbprint as Windows shows it. MD5 and SHA-1 digests and RSA and RSA-PSS keys under 2048 bits are marked as weak or broken. **Nothing is verified**: not the signature, the certificate chain, revocation or expiry, and the page says so. The image hash check below is not a signature check. A file can carry a certificate with any name in it, so treat these as the file's claims, and use `Get-AuthenticodeSignature` or Explorer's Digital Signatures tab for a verdict. The Signature section also shows the image digest the signature stores (for example "Image digest (SHA-256)") and an "Image hash check" row: MarkCopy hashes the file from the start to the end, leaving out the header checksum, the certificate-table entry and the certificate table, and says "The computed SHA-256 matches the stored digest.", "The computed SHA-256 differs from the stored digest.", or "Not checked: ..." with the reason. A match says only that the bytes are the ones the digest names; it does not say who signed the file, and a difference is reported without a cause. Only the primary signature is checked, not a nested one, and a Windows Installer package (.msi) is not checked. Files signed through a catalog (many Windows components) show as having no embedded signature.
- **Permissions and protections.** From the manifest, the requested execution level, UI access, DPI awareness and identity; from the headers, ASLR, high-entropy ASLR, DEP, forced integrity and AppContainer, and large address aware for 32-bit files. Control Flow Guard is checked against the image's guard data, not just the header flag, so a file that sets the flag without carrying the data is shown as such. Where the file records them, it also shows stack cookies (/GS), SafeSEH for 32-bit x86, EH continuation metadata, and CET shadow stack compatibility for x64.
- **Debug information, Build tools, Sections, Imports and Exports.** The PDB path and symbol ID, the tools Microsoft's linker recorded building the file (shown only when it left that record, and as a claim, not proof), the sections (long MinGW names such as `.debug_info` are spelled out), each imported library with a count of its functions and whether it loads at start or on first use, and the export count with the first 100 names.
- **Go.** For a program built by the Go toolchain: the Go version, main package and module, the build settings, and the modules it was built from (the first 200, with a count of the rest), as `go version -m` prints them. Files built by other toolchains show no Go section.

The file is **only read as bytes**. It is never run, loaded, or handed to the operating system, and there is no **Open in Default App** row in this preview's menu, because for an executable the default app is the file itself. A file on disk is read in bounded ranges, not loaded whole, with a budget of 16 MiB; the SHA-256 is computed for files up to 256 MB (a larger one shows "Not computed"), and a file on a virtual or remote file system is read whole and limited to 64 MB. A damaged or hostile file produces a notice or a warning, not a crash. Within a table, an entry that points outside the file is left out and the rest are shown, with a warning saying how many were skipped. A library whose function list cannot be read is listed as "Not counted".

It is built on the same shared shell as the Word and Excel previews, so right-click **Copy as Rich Text** and **Copy as Markdown**, a table's **Copy Table** (with Markdown, CSV, TSV and PNG under **Copy as**), **Save as PDF / Word / PowerPoint**, Reveal in file manager, the themes and Search Google all work. Its one setting is `markcopy.fileInfo.confirm`, shared with the [package info page](#package-info-preview).

Not shown: 16-bit and DOS executables (the page says so), Mach-O files (ELF and Mach-O files open in the [package info page](#package-info-preview)), the full list of imported function names, resources other than the icon, version block and manifest, signature verification, countersignature and timestamp details, and .NET metadata beyond the runtime version and flags.

## Files with the structure of two formats

Some files are valid as two formats at once: a zip appended to a Windows Installer package or an RPM, a zip with a disk image trailer, a PDF header and trailer inside a zip, a Windows executable with a zip appended. Many are ordinary (self-extracting installers, JARs with a launcher stub). The package and executable pages then show a notice at the top that names both formats and says where the second structure sits, for example "its central directory ends at the end of the file". Below the usual page, a section headed **Also read as: zip archive** shows the second reading. Only one extra reading is shown; if three formats match, the notice names them and says which one is read. If the second reading fails, one line says why. The notice describes structure only. It does not say how the file came to be that way. Right-click **Copy as Markdown** and the exports include both readings.

## Package info preview

MarkCopy registers as the editor for `.deb`, `.udeb`, `.rpm`, `.msi`, `.dmg`, `.pkg`, `.apk`, `.jar`, `.war`, `.ear`, `.vsix`, `.whl`, `.nupkg`, `.snupkg`, `.so`, `.dylib`, `.elf`, `.ko` and `.AppImage` files (either case) and `*.so.*` shared libraries, so opening one shows a page about the file instead of VS Code's "file is binary" notice (after you press **Read this file**, as above). It is for answering "what is this, what version, who made it, and what does it need?" before you install it. The format is decided by what the file holds, not by its name, so a `.jar` that is an Android library or a `.apk` that is an Alpine package is read as what it is.

Every page starts with the file's name, format and a one-line summary, and ends with a **File** section: format, size and SHA-256. What is in between depends on the format.

- **Debian package (.deb).** The control fields, the description, the dependency relations, which maintainer scripts exist, and the file list from the package's checksums. Only the control archive is unpacked (gzip, xz or zstd); the data archive is never opened.
- **RPM (.rpm).** The header tags, the description, the dependencies (internal `rpmlib` entries are hidden and counted), what the package provides, which scripts exist, the file list with sizes, a Payload contents row comparing the header's file list with the member names in the payload (gzip, zstd or xz cpio, up to 16 MiB compressed; it says whether they are the same, lists up to ten names of each difference, or says why it did not check), and whether an OpenPGP signature is present with its key ID. It also shows the digests the package stores of its own main header (SHA-1, SHA-256 and SHA3-256, when present) and of its compressed payload (when the header names the algorithm), each with a check row beside it: "The computed SHA-256 matches the stored digest.", "The computed SHA-256 differs from the stored digest.", or "Not checked: ..." with the reason (a stored value of the wrong length, an algorithm MarkCopy does not compute, a file that cannot be read).
- **Alpine package (a .apk that is gzip).** The `.PKGINFO` fields, the dependencies, which scripts exist, and the name of the signing key. The stored data hash is recomputed over the data archive (from where its gzip stream starts to the end of the file) and a **Data SHA-256 check** row says whether it matches or differs, or why it was not checked.
- **Windows Installer (.msi).** The product name, version, manufacturer, the product, upgrade and package codes, platform, the install context its properties request and what its summary flag says about elevation; how many merge modules were merged into it; how many rows its file, component, feature, registry, shortcut, service and custom-action tables hold; any embedded cabinets; and the Authenticode signer. These are what the package states, not a prediction of what an install will do: conditions and custom actions can change it. A patch, a transform or a merge module is labelled as one and nothing more.
- **Apple disk image (.dmg).** Size, compression, checksum type, the partitions, whether it is encrypted, and what its embedded code-signing data holds: a signature with a signer, an ad-hoc signature with none, or only a notarization ticket, which is not a signature. The file system inside is not read, so the app's name and version are not shown.
- **macOS installer package (.pkg).** The title, identifiers, versions, install location, whether it installs as root, the components and bundles, which components run scripts, the file list, and the names on its signing certificates.
- **Linux binaries (.so, .elf, .ko, .AppImage).** Type, architecture, interpreter, SONAME, build ID, whether it is stripped, for a Go program its Go version, package, module, build settings and modules, its protections (PIE, non-executable stack, RELRO, RPATH or RUNPATH, and Intel CET or Arm BTI and pointer authentication on those architectures), the libraries it needs, its sections, kernel module information for a `.ko`, and the payload size of an AppImage. An extensionless ELF file is not registered either; open it with **MarkCopy: Open as Package Info**, as for Mach-O files.
- **macOS binaries (.dylib).** Thin and universal Mach-O files, whatever they are named, though only `.dylib` is registered, so **Open With** does not list this editor for an extensionless executable. Right-click the file in the Explorer and choose **MarkCopy: Open as Package Info** (or run it from the Command Palette with the file open) to open it, or any other file the package page can read, this way. The type and architecture, the platform, minimum OS and SDK (every platform a library declares, such as macOS and Mac Catalyst, in either command format; an older binary's Intel iOS or watchOS slice, or x86_64 tvOS slice, is shown as a simulator build, as dyld does; an SDK recorded as 0 is not shown), the build tools, UUID, source version, install name and versions, dynamic linker, entry point, whether it carries a code signature (not verified: present, declared but empty, or declared with its data outside the file) and whether it is encrypted, its protections (PIE, executable stack, the `MH_NO_HEAP_EXECUTION` flag shown as set or clear, with the platform default applying when it is clear, a `__RESTRICT,__restrict` section, code signature). When a cap or a damaged command stopped the reading of the load commands, a signature, encryption or `__restrict` section that was not seen is shown as unknown, not as none, the libraries it loads with their kind and version, run paths, and segments. A universal binary adds a table of its architectures (type, minimum OS, UUID, offset and size) and describes the first one in full.
- **Java archive (.jar, .war, .ear).** The manifest, the Maven coordinates if the build left them, the class count and the Java version, and the JAR signer.
- **Encrypted zip entries.** When any entry in a zip-based package is encrypted, the **File** section gains an **Encryption** row such as "12 of 40 entries: AES-256 (WinZip AE-2)", when only part of the archive directory could be read it says "1 of the 1 entry read: ..." and counts the entries read, counting each method (AES-128, AES-192 or AES-256, PKWARE strong encryption, or "ZipCrypto (legacy, easily broken)"). It is a label only: MarkCopy never asks for a password and never decrypts an entry, and the label says nothing about whether the file is safe. An encrypted entry that the page would have read (a manifest, say) is skipped with a warning that it could not be read.
- **VS Code extension (.vsix).** Identity, the engine it needs, activation events, and counts of what it contributes. An extension's Marketplace signature is a separate file, so it cannot be seen from the VSIX and the page says so.
- **Python wheel (.whl).** The metadata, the requirements and the entry points. It also lists the startup files (`.pth` and `.start`) and says whether each runs code when Python starts; where that depends on the installer, on the installation scheme or on a part of the archive that could not be listed, the page says so.
- **NuGet package (.nupkg, .snupkg).** The nuspec, the dependencies by framework, whether it carries build or install scripts, and the signer.
- **Android package (.apk).** Package name, versions, SDK levels, permissions, components and how many of them are exported, native ABIs, which signing schemes are present, and a DEX files section (file count, format versions, and the classes, method references and strings the headers state). For the first DEX file the page recomputes the checksum and SHA-1 stored in its header and says whether they match, or why it did not check.
- **Any other zip.** The contents only.

The file is **only read as bytes**. It is never installed, run, mounted, or handed to the operating system, and there is no **Open in Default App** row in this preview's menu, because the default app for a package is an installer, and for a `.jar` or an AppImage it is the file itself. Reads are in bounded ranges of 64 KiB pages, with a budget of 32 MiB per file, so a multi-gigabyte installer costs its headers. The SHA-256 is computed for files up to 256 MB (a larger one shows "Not computed"), and a file on a virtual or remote file system is read whole and refused above 64 MB. Decompression stops at a fixed size. A damaged part of a file becomes a warning on the page, and a file that is not the format it claims becomes a notice.

**Scripts are never shown or run.** The page says only that they exist, because that is what tells you an install will run code, and for most of these formats it runs as root.

**A stored-digest check is not a signature check.** A match says only that the bytes are the ones the stored digest names. The digest sits in the same file, so it says nothing about who made it, and a difference is reported without a cause. The check is skipped over 256 MB of covered data.

**Signatures are reported, never verified.** The page says who the file names as its signer and that nothing was checked. A file can carry a certificate with any name in it, so treat these as the file's claims. An Android package signed with scheme v2, v3 or v3.1 shows the first signer's certificate from the APK Signing Block (the newest scheme present wins), with its signature algorithm and a count when there are several signers. When more than one scheme is listed, a **Certificate from** row names the scheme the shown certificate was read from, because a v3.1 rotation can hold a different key from v3. An RPM signature is OpenPGP, so it has a key ID and no certificate name.

It is built on the same shared shell as the Word and executable previews, so right-click **Copy as Rich Text** and **Copy as Markdown**, a table's **Copy Table** (with Markdown, CSV, TSV and PNG under **Copy as**), **Save as PDF / Word / PowerPoint**, Reveal in file manager, the themes and Search Google all work. Its one setting is `markcopy.fileInfo.confirm`, shared with the executable info page.

Not shown: the symbols and entitlements of a Mach-O binary, the app inside a disk image, an Android app's label and icon, the contents of any script, and signature verification. A Debian package whose control archive is compressed with bzip2 or lzma shows a warning instead of its fields.
